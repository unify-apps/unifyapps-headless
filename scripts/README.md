# scripts/

This folder holds the Node code that ships with the plugin. Claude runs it through skills, hooks and MCP servers. None of it is a test or a build tool; those live in `builder/`.

## How the folder is laid out

- **Files at the top are files you run.** Other files call them by path: `hooks/hooks.json`, `.mcp.json`, skills, and older UnifyApps Headless versions during an update. Do not move or rename them.
- **Folders hold code that is only imported.** Each folder is named after what its code touches.

| Folder | What its code touches |
|---|---|
| `cmd/` | Nothing on its own. One file per `ua.mjs` area (`solution`, `spec`, `plan` …). |
| `lib/` | Nothing. Pure functions only: no files, no network, no output. |
| `platform/` | The tenant (the UnifyApps platform) over HTTP, or the local copy that stands in for it. |
| `workspace/` | The working folder on disk: the shared solution home and each session's `.sessions/<id>/`. |
| `transcript/` | One Claude transcript, for `session save`. |
| `release/` | The list of files a release ships. |

A call usually goes: an entry point → `cmd/` → `workspace/` and `platform/` → `lib/`. Code in `lib/` never imports from the other folders.

| `mcp-bridge.mjs` | Runs one tenant MCP server (`application-builder`, `object`, `automation-code`, `agent-builder`, `app-testing`, `connection`, `solution`, `evaluation`, `api-gateway`, `connectors-sdk`, `changeset`, `code-builder`, `context-graph`) over stdio. Refuses the one call that would send a real request under `UA_FAKE=1`, since it has no fake tenant of its own and would otherwise send real traffic past a faked verdict. Finds the tenant from a working folder — the one its Claude session opened UnifyApps Headless in (or signed in to a tenant in), or else the one it runs in; the calling session is the one the `SessionStart` hook recorded for the bridge's Claude Code process (`workspace/claude-process.mjs`), else the one the bridge started with, and its own row in the folder names the call before the folder's newest; a folder that holds a solution names it on every call, sign-in or not, and a sign-in entry with no solution yet gives the tenant alone, so the tools are listed during setup; a folder with neither but a tenant binding goes to that tenant and passes on only `TENANT_ONLY_READ_TOOLS` (`lib/contracts.mjs`), lists only those, refuses every other call before anything is sent, and marks no cache — then adds that tenant's saved or default URL, cookie and the `x-ua-` call context headers (`x-ua-session-id`, `x-ua-solution-id`, `x-ua-plugin-version` and `x-ua-check-versions`, built by `clientHeaders()` from the context's identity and nothing else; nothing about the person beyond the sign-in cookie, the machine or the AI client's account, and no `x-ua-agent-kind`, since one process serves the main session and every builder) to each request and passes the call itself through unchanged. A tool list that fails (signed out, a 5xx on the environment check) answers with the last list this process got, since Claude Code fixes a builder's tools when it starts it; with no list yet it asks Claude Code to list again after 15 seconds, then twice as long each time up to every 5 minutes. Every call gets a minute, except `deliver_steps` on `app-testing`, which runs a browser and gets 450 seconds, `trigger_workflow_run` 150, `send_test_messages` 900, and the page writes `apply_page_edits`, `create_pages` and `create_data_sources` 180, `upload_public_file`, which sends up to 20 MB, 180, the evaluation run reads `experiment_scorecard` and `get_run_results` 180, the API Platform `call_api` 180, the agent-builder `upload_file` and `add_knowledge` 180, `update_knowledge`, `list_knowledge_apps` and `delete_knowledge_sets` 120, the CLI's own `get_app_entities` read 150, and the code-builder calls that run the engine's build or move a whole codebase (`push_code_patch` 360, `publish_code_app` 480, `get_branch_codebase` 150, `create_code_app_data_sources` 130 for each source it asks for and a minute more, `create_code_app` 120) (`TOOL_TIMEOUT_MS`). A call that runs out of time says a write may still have landed and to read the item back first. The tenant tools refuse stale writes themselves. Seven exceptions; the seventh is code-builder: a `get_branch_codebase` reply is unpacked into a local checkout at `<appId>/<branch>` in the working folder (`workspace/code-checkout.mjs`) and the model gets the folder back instead of the zip; a call that names the branch of an existing checkout is a pull, sent with that checkout's commit as `since`, and the one patch it answers is applied to the checkout, or the whole branch is downloaded when the checkout cannot take it. `push_code_patch` may take `localPath` (and `resolved`), sending that checkout's whole change as `patch`, with the checkout's commit as `base`, on the checkout's own app and branch and moving its base to what a green push committed. `create_code_app_data_sources` may take `localPath` too: the bridge does not send a source the checkout already has (Storage bindings that name a `FETCH` id, an automation's block in `callables.ts`), and writes the files the call answers into the checkout instead of handing them to the model. `list_code_skills` and `read_code_skill` answer Code Builder's own skills from the tenant's engine, and their replies pass `lib/skill-scan.mjs` first: flagged text is withheld and the reply says so. The other six: Every create gets the `UnifyApps Headless` tag beside the tags it sends (`withUaTag`): `create_app`, `create_agent`, a `compile_and_save_workflow` with no `workflowId`, each `create_object` step of `apply_object_batch`, and each set of `save_knowledge_sets` with no `knowledgeSetId`; an update keeps its own tags, since tags sent there would replace the ones the item has. Every app, code app, global module, package, object, automation, AI agent and connection a call creates is linked to the folder's solution with its `solution_linked_assets` row before the reply goes back (`withCreatedLinks`, writing through `linkEntityRefs` in `workspace/entity-cache.mjs`), read from the reply by `createdEntityRefs` in `lib/mcp-entity-changes.mjs`; a folder with no solution yet links nothing, and a link that fails never fails the call: the reply gains one line naming the `entity read` that links it. `apply_page_edits` may take its arguments from a JSON file (`argsFile`), and the bridge checks them with `lib/page-edits.mjs` before anything is sent. `compile_and_save_workflow` may take its code from a `.ts` file (`codeFile`), sent as `code`. `open_workflow` may write the code it returns to a `.ts` file (`outFile`) and answer `codeFile` instead of `code`. `update_app_settings`, `set_app_theme` and `set_theme_typography` may take their arguments from a JSON `argsFile` too, for a long custom code header or a theme, and `save_skill` its body (`bodyFile`) and `create_agent`, `update_agent` and `save_task` their instructions (`instructionsFile`) from a `.md` file, so a long text is never retyped into one call (`ARGS_FILES`, `TEXT_FILES`). `upload_public_file`, and `upload_file` on `agent-builder` only (another server may name a tool `upload_file` too), may take its file from a local path (`filePath`), sent base64 as `contentBase64` with the file's own name as `fileName`, at most 20 MB. Every file must sit in the working folder the bridge serves, the folder it runs in, or a temp folder, compared by the disk's own path so a different letter case still matches. `open_workflow` may answer up to 500,000 characters, so a long automation comes back whole. A key the API Platform answers once in `secret` (`save_access_profile`, `rotate_access_profile_key`, `create_oauth_token`) is written to `.sessions/<sessionId>/secrets/` in the working folder, owner-only, and the reply names that file as `secretFile` instead, so no model sees the key (`keepKeyOut`). A tool's refusal for the `AGENT_LLM_TOOLS` permission (the fixed sentence llm-tools answers in any of its error envelopes, `isPermissionRefusal`) is thrown as `PERMISSION_REQUIRED` once the sign-in is checked with `verifyCookie`, whose verdict is kept 30 seconds per tenant and cookie, so a script refused 150 times reads it once. A sign-in answered 401, 403 or with no person in it is `AUTH_EXPIRED`. Otherwise the line names the tenant, the tool, the person and the permission, says a tenant admin must add it when the role lacks it, and that the tenant refuses the same way when it could not read the role's permissions just then, so a person who holds it can send the call once more after a minute; a sign-in the check could not read is said too. A tenant reply over 100 MB is not read past that point and comes back as `REPLY_TOO_LARGE`, so the CLI's own in-process reads (a whole app from `get_app_entities`) can take up to that much; no line the bridge writes to Claude Code is longer than 15 MB, because Claude Code closes a server whose reply line passes 16 MiB, so a bigger tool reply comes back as `REPLY_TOO_LARGE` too. Once the arguments are valid, it marks that page's local interface cache stale before forwarding the edit, so an ambiguous or lost remote response cannot leave pre-edit data looking current, and once more when the answer comes back, so a refresh that read the page while the write was still landing cannot clear the mark; every other application-builder write (navigation, settings, theme, page paths, event actions, data sources, publish) marks the whole app stale, an object write (`apply_object_batch`, `delete_object`), an automation write (`compile_and_save_workflow`, `deploy_workflow`) and an AI agent write that names its `agentId` (`AGENT_WRITES`, giving or taking a knowledge set among them) mark their folder copy stale the same way (`CACHE_WRITES`, each name checked against the live tool list), and a dry run marks nothing. The application-builder `get_app_builder_knowledge` read asks again for every sheet the tenant left out to keep one reply small, and joins the pages into one reply with `lib/knowledge-pages.mjs`. It asks for at most 25 ids per page, the tool's own `nodes.maxItems` from the live tool list, and splits an agent's own ask that names more. It stops after 20 pages, 480,000 characters or 120 seconds, and any id it did not get to comes back in `omitted.budget`. It also raises that tool's reply size limit in Claude Code to 500,000 characters. And on application-builder, `get_app_builder_knowledge`, `apply_page_edits` and `update_event_actions` take an `agent` name (the builder name from its message, or `main`). The bridge keeps each builder's token list in memory only, for the life of the bridge process, which is the Claude session, with `lib/knowledge-tokens.mjs`: every token a read or a refused write hands over goes on the list, a read sends the list with its own `have` (only `have: []` goes as sent, to get the text again, and it starts that builder's list again from that read, since a name alone cannot tell a new builder from an old one), and a write sends the list with its own `knowledgeTokens`. A refused write that hands over `sheets.tokens` has the tenant's advice to send `knowledgeTokens` replaced by: send the same call again. A refused write of a builder the bridge holds no list for (the process started again mid-session, as on a plugin update, while the builder still holds the sheets) gets a `bridge` line saying so and telling it to read those sheets again with `have: []`; nothing is saved to disk, so a list is never trusted for a builder whose context was cleared. The tools' schemas tell a builder to leave `have` and `knowledgeTokens` out. `agent` is never sent to the tenant, and one builder's list never reaches another's call. | `.mcp.json`, `.claude-plugin/plugin.json` |

## cmd/ — one file per CLI area

Each file exports `run(command, args, flags, ctx)`. `ua.mjs` picks the file by the first word of the command.

| File | Commands |
|---|---|
| `state.mjs` | `state next`: what setup step comes next (tenant, sign-in, solution). |
| `solution.mjs` | `solution resolve`, `handoff` (makes a new folder and writes its handoff file under the UnifyApps Headless home's `handoffs/`, so the next `/ua:setup` there opens the chosen solution), `handoff-claim` (claims that handoff for one session, or gives the claim back with `--release`), `find`, `locate` (where each linked entity lives, as facts), `storage-check`, `open`, `create`, `refresh`, `mcp-setup`, `context`. |
| `task.mjs` | `task begin`, `update`, `get`, `end`, `note`: the session's current task (request word for word, outcome, phase, approvals, pieces sent to builders, done pieces with the read-back that names their entity) and its last 20, kept in `state.json` so a compaction or resume picks it back up. `--sent --agent` makes that builder's work folder. `note --decision`/`--question` adds to the session ledger (`lib/ledger.mjs`); a `--done` also fills the ledger's entities. |
| `spec.mjs` | `spec check`, `draft`, `accept`, `revise`, `get`, `list`. |
| `fast.mjs` | `fast brief`, `fast accept`: kept names for `spec draft` and `spec accept`, one format and one accept path. `fast accept --execution plan` (the one value, optional) records that a plan follows on the session state, which `solution context` returns as `execution`. |
| `plan.mjs` | `plan create`, `revise`, `audit`, `fork`, `interrupt`, `start`, `resume`, `mark-failed`, `ready`, `task`, `report`, `confirm`, `reclaim`, `finish`, `get`, `list`. `ready --mark` marks the ready batches running in one write and writes each builder's message file. |
| `plan-propose.mjs` | `plan propose`: checks a spec and its tasks (or a short change of one or more tasks on existing entities) locally, reads the solution's plans from the tenant once for the overlap check (`findOverlaps`; a failed read falls back to the local copy with one line), writes and opens the preview only with `--preview`, and keeps `pendingSave` on the session. Every answer lists `overlaps`: running plans of other people or sessions that touch one of the same entities, named by email and last activity, as a fact, never a refusal. `--save --hash` chains spec draft, spec accept and plan create, each safe to rerun, with at most one solution sync; `--go` does the same after a yes in chat and then starts the plan. |
| `entity.mjs` | `entity read`, `list`, `context`: the local copy of the apps, objects, automations and AI agents linked to the solution. `read` takes one id, a comma list or one id per argument, and links every one it read in one solution write; `read code-app <appId>` links a code app as its interface record. `context` answers from the cache alone — the whole solution as names, or one app, page, object, automation or AI agent, named by id or by name, with `hit`, `miss` or `stale` — so a question is answered from the copy before the tenant, and a task that creates an entity and has only its name gets `miss`, not a usage error. `context --save` is a builder's read before a write: it first reads that one app (as a version delta) or entity from the tenant, since the cache knows only UnifyApps Headless's own writes and an edit in the builder or a publish made elsewhere would otherwise answer `hit`, and answers `stale` with `liveCheckError` when that check fails; a plain `context` stays offline. | `entity-cache.mjs` | Saves versioned copies of apps, objects, automations and interface children under `entities/`, links top-level entities to the solution, and coordinates solution refreshes. Serves the `entity context` reads, and keeps the stale markers an object or automation write leaves under `entity-manifests/entity-dirty/`, cleared only by a read that started after them. A page or app checkpoint also refreshes that one app's interface cache, so a page task's report leaves the page and its data sources current. Each copy is its own `<id>_<version>.json` and no write replaces one, so `cacheEntity` keeps the newest `KEPT_ENTITY_VERSIONS` (10) per entity and removes the rest: `readCachedEntity` lists the whole type folder on every read, and a folder worked in for months would otherwise hold every version it ever read. The write lands before the trim, so a crash between them leaves an extra old version, never a missing current one. A refresh reads the entities the solution links; a copy it does not link is read only while it is newer than `UNLINKED_REFRESH_MS` (6 hours), which covers a builder's new entity before the reporting step writes its link row, or while a write has left it marked stale and a read must make it current again. An older unlinked copy is left on disk and served, just not re-read, so a refresh costs what the solution holds rather than everything the folder ever cached. The objects, automations and AI agents of a refresh are read by kind through `get_definitions`, one call each, sending the version of every copy held: a solution of 100 of them is 2 calls instead of 100, and transfers nothing at all when nothing changed. A copy with no version yet is left out of `knownVersions` rather than sent as `-1`, so an entity still at version 0 comes back; a copy held at version 0 sends 0. A kind with more entities than `MAX_DEFINITION_IDS` (200) is read a page at a time, because the tool's own schema refuses a longer list outright. The markers of every id asked about are cleared, not only those that answered with a record, because an entity reported unchanged is current on disk and would otherwise read `stale` for good. An id in `gone` keeps its copy and is marked, never pruned: the tenant answers `gone` both for an entity that no longer exists and for one this sign-in cannot see. A page the tenant will not answer — a tenant whose llm-tools predates the tool, a reply too large, a batch that ran out of time — is read one entity at a time instead, per page, so a kind it cannot answer never stops the others; a sign-in that ran out ends the refresh instead, as it did when each entity was read on its own. |

## Adding, moving or removing a file

1. **A file you run** goes at the top. Once it ships, treat its path as fixed.
2. **A file you only import** goes in the folder that matches what it touches. If it touches nothing, it goes in `lib/`.
3. **Update this README in the same change.** A test fails when a file in `scripts/` is not listed here, or when this README lists a file that is gone.
