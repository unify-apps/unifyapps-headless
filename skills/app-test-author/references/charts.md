# Charts — locating and asserting on rendered data visualizations

Loaded the moment a scenario involves a chart, graph, or plotted visualization (hovering points, reading tooltips, counting bars or slices).

**Chart data points are positional by nature — slot-encode them, never data-anchor them.** A point, bar, slice, or tick inside a rendered chart (Recharts, Victory, ECharts, any SVG framework) exposes only transient, data-derived hooks: coordinate attributes (`cx`/`cy`, `transform`, a path's `d`), value-bearing accessible names ("Jun: 790"), paint order, per-render ids (`recharts-*`) — every one changes when the data changes, so every one is **banned as an anchor** (the derivation rule's locator-side twin). The faithful encoding is the slot: the chart container by its durable hook → bare-tag links through the series scaffolding (`g`, `path`, `rect`, `circle`) → `:scope > :nth-child(n)` for the point/bar — "hover over a point on the trend line" is a generic pick (slot index 1), "the third bar" is the stated slot; this is the positional class of _The scenario names the anchor_, and the nth-child slot link is mandatory here, not last-resort. The same ban binds **assertions**: never assert a coordinate, a path string, or a value-bearing name read from chart geometry — chart values are verified through the read surfaces the chart exposes (the tooltip the hover opens, **surface-scoped** per the assert HARD RULE; a legend; an axis label only as a design constant), with the values under the litmus as always: `text_not_empty` or a JS numeric check on the tooltip's value node, never today's reading.

**Hover-tooltip recap** (canonical rules in the main instructions — the surface-scoped assert HARD RULE): a hover that opens a tooltip is an acting step recording the reveal on the tooltip marker it opens; every value check targets nodes INSIDE that marker (`text_not_empty` / a JS numeric check), never `text_on_page`; and the observed reading never enters the payload (the litmus).
