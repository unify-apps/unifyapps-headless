You are running the platform's Test-Author doctrine locally, in Claude Code. The main session walks the app with the Playwright MCP; a `test-author-agent` helper uses `playwright-cli` instead, and its agent file maps the MCP column below onto it. The platform's app-testing tools are the plugin's `app-testing` MCP server, as `platform-tools.md` explains; the platform agent's own tools (`Deliver Steps` and the rest in the table below) are not here. `references/local-rules.md` is the rulebook — mechanically derived from the platform agent's canonical instructions (platform-only sections removed at build time; nothing hand-edited), so every authoring rule in it binds verbatim: grammar, locator vocabulary, assertion doctrine, readiness, derivation, random data, JS governance, safety. This file translates the tool names it uses to your environment and adds the local-only phases. Where the two conflict, THIS file wins.

## Which dialect file

The platform agent receives a `testSubject` (`'interface-builder' | 'interface-code' | 'platform'`) in its context; locally nothing is sent, so you detect the subject from the app's first signed-in page — one `browser_evaluate`, in this order:

1. **Platform** — the app IS the UnifyApps platform UI (managers, editors, settings — the product itself, typically at `<tenant>.unifyapps.com/p/<n>/…`). Tell: the platform shell — `document.body.classList.contains('is-platform-shell')`, or a `[data-nav-root]` / `[data-testid="nav-root"]` side navigation. Present → read `references/platform-dialect.md`. It is a hybrid: manager and shell surfaces use component markers; entity config/edit surfaces are builder-rendered and carry the full `data-block-*` DOM — the platform dialect tells you when to additionally read `references/builder-app-dialect.md` for those regions (it stays the governing file).
2. **Builder app** — no shell, and `data-block-id` / `data-block-type` on elements throughout → read `references/builder-app-dialect.md`.
3. **Code app** — no shell, no `data-block-*` anywhere → read `references/code-app-dialect.md`.

Read the matching dialect BEFORE authoring any element — its hook ladder, hydration/race doctrine, and decoy patterns bind with full force locally. If a later surface contradicts the detection (a builder DOM on a "code" app), note it in `observations`, trust the DOM, and read the matching dialect before authoring there. Wherever a dialect file speaks of `testSubject` or of loading a skill, read it as this detection and as reading the named reference file.

Element objects are `{ "pageUrl", "locator", "name" }` — as the rulebook's payload rules state, never candidates, never a `label`.

## Resolving the user id

Every submission's `userIds` starts with the id of the account whose signed-in session the walk used, normally the test user the sign-in flow signed in as (SKILL.md, _Sign in as a test user_); a public app (no session) sends `userIds: []` (submission contract). You resolve every id yourself; **never ask the user for it, never scrape it from the UI, never infer it from a URL or an email.** Once the browser session is signed in (after the test-user sign-in, and again after any re-login as a different account), run one `browser_evaluate` on the app's own origin:

```js
async () => {
  const r = await fetch('/api/user-context?includeRoles=false', { credentials: 'include' });
  if (!r.ok) return { status: r.status };
  const j = await r.json();
  return { status: r.status, userId: j?.user?.id ?? null, keys: Object.keys(j?.user ?? {}).slice(0, 30) };
}
```

- The user id is **`user.id`** in the response (a string). Take it verbatim; that is this test user's `id` in the run file's `users`.
- `status` 401/403 (or a redirect) → there is no signed-in session. **If the app has a login wall**, the session has lapsed: repeat the test-user sign-in (SKILL.md, _Sign in as a test user_ — refill a created user's credentials, or pre-fill an existing user's handle for the password) and re-run the call once. **If the app is public** — it never presented a login wall and the walk proceeds without one — this is the expected result: **send `userIds: []`** in every submission walked in that state (never `null`, `""`, `anonymous`, or any placeholder id), note "public app — no user id" once in the report, and carry on. Never invent an id and never sign in to an app that needs no login.
- `userId` null with a 200 → the shape changed; read the returned `keys` (and, if needed, one more evaluate over `j.user` returning key names and value TYPES only — never dump the object) to find the user's own id field, use it, and record the field you used in your report. Ask the user only if no id-like field on the user object can be identified.
- This is a **read-only GET on the app's own origin** — one of the four sanctioned non-UI requests (SKILL.md, Boundaries). Never write it into a test step, never change its method or body, never call another endpoint. Do not print the response — the user record contains personal details; the id and the status are all you need.

No `applicationId` is collected, asked for, or written anywhere. The submission's `interfaceId` comes only from the sanctioned read-only `GET /auth/interface/deployed` on the app's own origin, or is the platform literal the submission contract names when the subject is the platform itself (SKILL.md, submission contract) — never asked for, scraped from the UI, or guessed.

## Naming a generated test user

A person reads these names in Test Studio and in chat, so they say who the user is and carry no random characters. Build them from the app and the role the user plays in it: the app's short name plus the role, lowercase and hyphenated, for the username (`chat-sender`, `chat-recipient`, `expenses-approver`; plain `<app>-tester` when the app has only one role), the same words in title case for the name (`Chat Sender`), and an email whose local part is the username. Before the create, `list_test_users` with `testUsersOnly=false` and check the username is free; when it is taken, or the create answers that it is, add the next free number (`chat-sender-2`), never a random string. Only the password is random.

## Self-provisioning — no dependency on pre-existing data (HARD RULE; wins over the rulebook)

**Every scenario creates the data it verifies. A test never depends on records it did not create in its own steps.** This binds Phase 1 (what a scenario may say) and Phase 2 (what a step may reference) with equal force, and it overrides the rulebook's "scenario-stated literal" license wherever the stated literal is an existing record's name, position, count, or membership.

**Why this is a hard rule, not a preference.** A test that reads today's dataset fails in exactly two ways, and both are worse than no test: (1) it **cannot catch a regression** — "searching 'Deviation' leaves one row" passes for as long as one such object exists, whatever the search does; "applying the filter leaves fewer rows" passes for any filter that removes anything; and (2) it **goes red when the data moves while the feature works** — someone renames that object, moves it to another tab, or the tenant has one record and "sort changes the first row" cannot be true — and the red says *the platform is broken* when it isn't. Random per-run identities are what make the assertions sound (rulebook: _Assert the record you created_); this section makes that shape the ONLY shape.

**The dependency is illegal in every disguise — the litmus is the same in each:** *if every record the test did not create were deleted before the run, would the scenario still be provable?* No → it is data-dependent, whatever the phrasing.

| disguise | example | why it is still a dependency |
|---|---|---|
| a named existing record | search "Deviation" leaves exactly one row; click the "Northwind Launch Plan" row | the record is someone else's; rename or delete it and the test lies red |
| a witness of membership | "Invoice Import Staging" appears only on the Standard tab | moving that object to Custom is legitimate; the test would call it a bug |
| a relation to today's dataset | filter "narrows the table to fewer rows"; sort "changes which row appears first"; view "narrows to fewer rows than Main" | assumes today's dataset contains both kinds / more than one row — false red on a small or uniform tenant, false green on any change |
| an observed count as the cross-check | Columns value (17) equals the Schema tab's field rows | 17 is someone's data; the test controls neither side |
| an existing saved view / tag / workspace | switch to the "Open Orders" view | shared, editable state — deleted by anyone at any time |
| "relational phrasing" of the above | "the row count matches the header total" over existing rows | still proves nothing about the feature when the dataset is empty, and still red on concurrent edits |

**The mandatory shape — create → act → verify → (delete own).** The scenario text itself says what it creates; the steps do it first.

1. **Create** the record(s) the feature will operate on, through the app's own creation UI walked for real: `store` `from: "literal"` `value: "<<random:12>>"` `into: <identity>` for every field a later step reads, `fill` with the `<<var>>`, satisfy required fields, submit, readiness pair. The identity field gets ≥ 12 characters so it never collides with other data or earlier runs.
2. **Act** — the feature under test (search, filter, sort, tab switch, view, open, edit, action menu) is exercised **against the created records, found by identity** (`fill` the search/filter with the `<<var>>` → readiness pair → `count eq 1` on the row → act on `:scope > :nth-child(1)` of the filtered set; rulebook _Other patterns_).
3. **Verify** through the same `<<var>>`s. Never a literal name, never a literal count, never "fewer than before".
4. **Delete own (when the app offers it and the walk performed it)** — the last steps remove what the test created, via the app's own delete on that record; deleting the test's own data is in scope. A run that fails mid-way leaves a random-named residue that harms nothing; say so once in `observations`. Never delete anything the test did not create.

**Worked shapes — per feature class (locators illustrative; measure your own):**

- **Search:** create one record `<<name>>` → search `<<name>>` → pair → `count eq 1` on the row → row `text contains <<name>>`. The rulebook's "never randomize a search box" stands — this is the find-by-identity pattern, not randomizing.
- **Filter by property:** create record A with the property set to value X and record B with value Y (both fields test-typed) → apply filter `X` → pair → search `<<nameA>>` finds it (`count eq 1`); search `<<nameB>>` in the filtered set finds nothing (`count eq 0` on the row, or the empty-state marker visible — negative asserts only after the pair). Where the scenario asks only for the badge (`Filter (1)`), that label is a design constant and needs no record.
- **Sort:** create two or more records sharing ONE stored random prefix — `store` `<<random:10>>` → `prefix`, then names `<<prefix>>-A` and `<<prefix>>-B` — → **isolate first**: search `<<prefix>>` → pair → `count eq 2` → sort ascending → first row (`:scope > :nth-child(1)`) `text contains <<prefix>>-A`; sort descending → first row contains `<<prefix>>-B`. Sorting the unfiltered table asserts an ordering over other users' data and is banned. For created-time sorts, creation order is the test's own ground truth.
- **Tabs / segments / categories (Custom vs Standard, Active vs Archived):** create a record that belongs to category X → on tab X, search `<<name>>` → `count eq 1`; on tab Y, search `<<name>>` → pair → `count eq 0` / empty state. Never a witness record from either tab. A bare "switching tabs loads a different set" scenario is a structure check — assert the tab's `aria-selected`/`data-selected` and the new region's shell, no records at all.
- **Saved views / tags / any shared config:** the test creates the view (random name) → searches the view list for `<<viewName>>` → switches to it → asserts → deletes it. An existing view is never referenced.
- **Cross-checks (a count vs the parts it summarizes):** the test creates the entity WITH a number of parts it chose (an object with 3 fields, a ticket with 2 comments) → both sides are test-controlled — assert the list's count cell `displayed_value eq 3` and the detail tab's repeated item `count eq 3`, or store-and-compare between them. A cross-check over an existing entity is out.
- **Detail navigation, activity, back:** create → find by identity → open → assert the detail heading `text contains <<name>>`; the activity timeline of a just-created record shows a "Created" entry (`count gte 1` on the entry item, or `text contains "Created"` on the timeline container) — never "All N" of an existing object.
- **Row actions (edit, share, delete):** in scope on the record the test created — the do-not-touch rule protects OTHER data. Walk them, author them, assert their outcome by `<<var>>`.
- **Legitimately data-free scenarios (no records needed, no exemption needed):** form validation (button disabled until a required field is filled), auto-fill derived from what the test typed, labels/headers/option sets, shell mounting after a tab switch, a cancel/back that discards a draft. Structure and test-typed values are yours; only pre-existing records are not.

**No creation path = not covered.** When the app or the signed-in role offers no way to create the record a feature needs (system-defined "standard" entities, a read-only role, creation behind a wizard the walk cannot complete), the scenario goes to "not covered, and why" with the reason *requires pre-existing data; no creation path*. Never fall back to an existing record, never rephrase the dependency relationally to smuggle it through, never mark it "fragile" and author it anyway.

**Scenario text must name the provisioning.** A scenario that does not say what it creates is data-dependent by construction. Rewrite table (the left column is the kind of scenario a run tends to produce):

| data-dependent (rejected) | self-provisioning (accepted) |
|---|---|
| Searching "Deviation" leaves exactly one row ("Deviation"). | Create an object with a random 12-character singular name, return to the Custom Objects table, and search for that name; the table shows exactly one row and it contains the name. |
| Choosing "Is Standard" / "Is" / "True" and clicking Apply narrows the table to fewer rows and changes the button to "Filter (1)". | Create a custom object with a random name. Apply the filter "Is Standard" = "True" and confirm the button reads "Filter (1)"; searching the created name in the filtered table finds no row. Clear the filter and search again; the row is back. |
| Switching the sort order to Ascending changes which row appears first. | Create two objects named `<prefix>-A` then `<prefix>-B` (one random prefix). Search the prefix so only those two rows show; sort Name ascending and the first row is `<prefix>-A`; sort descending and it is `<prefix>-B`. |
| "Invoice Import Staging" and "Approval Log" appear only on the Standard tab. | Create a custom object with a random name. On the Custom tab, searching the name finds one row; on the Standard tab, searching the same name finds none and the tab's empty state shows. |
| For "Northwind Launch Plan", the Columns value (17) equals the number of Schema-tab field rows. | Create an object and add three fields to its schema. Back in the objects table the created row's Columns cell shows 3, and its Schema tab lists exactly 3 field rows. |

## The readiness pair is unconditional after every navigation (HARD RULE; wins over the rulebook)

The rulebook scopes the post-navigation readiness pair to "query-driven pages" and motivates it by point-in-time reads. Locally that scoping is **removed**: **every `navigate`, every `reload`, and every click that carries `navigatesTo` is followed IMMEDIATELY by the readiness pair — settle (`wait_for_hidden` on an observed loader, else `wait_for_ajax`) then `wait` `2` — before ANY step touches the destination: a `fill`, a `click`, a `store`, an assert, anything.** There is no "static page", "plain form", or "not query-driven" exemption, and you never classify a page as one: on this platform every page is an SSR shell whose content mounts client-side, and a form is not exempt because it shows no table.

Why the exemption is a trap, from a real run (7 of 7 rows red): `navigate /objects/create` → `fill` the Singular name field → `click Create object` timed out for 120 s. Playwright's log: the button resolved, then *"element was detached from the DOM, retrying"*, then resolved again **disabled**. The `fill` succeeded — actionability only checks visible/enabled/editable — against the pre-hydration input; the client then re-mounted the form, the typed value was gone, and the submit stayed disabled forever. `fill`'s "own actionability wait" proves the element is there, never that the app is listening to it. The pair after the navigate is what closes that gap, and it is cheap: the settle exits on idle, the grace is a flat 2 s.

Three corollaries:

- **A `navigatesTo` click is a navigation** — the pair follows it before the first action on the landing page (the create form reached through "Create object" needs the pair exactly like a `navigate` to its URL).
- **There is no execution-time budget to trim pairs against.** A payload is never "kept lean" by dropping readiness; a reasoning line like "well inside the 30 s budget" is a defect signature — the test ran 120 s red instead. Each pair costs ~2 s; a 30-step payload with eight pairs is fine.
- **One exception: a loader the scenario asserts.** A `delay` rule (`network-rules.md`) holds the call behind it, and the triggering step is followed by that loader assert, then the pair: the settle would otherwise wait the loader away before the assert reads it. Check 7 accepts that loader assert between the navigation and the pair.
- **Pre-flight check 7 (mandatory, alongside the rulebook's five and the self-provisioning sixth):** for every `navigate`, `reload`, and `navigatesTo` step, the next two steps are the pair. Any of them followed by a `fill`/`click`/`store`/assert is a defect — fix before submission. The rulebook's refetch rule stands unchanged on top: every filtering, searching, sorting, saving, or state-mutating action also gets the pair before the next read. An `open_window_and_navigate` is a navigation too: the pair runs in the new window. Check 9, that every assertion carries its description's outcome with the same subject and polarity, is in `durability.md`.

## Walk discipline — refs, reads, and dirty forms (HARD RULES, measured from real runs)

**Refs are one-shot.** A ref is valid only until the next action that changes the page — a click, a fill that re-renders, a navigation, a dialog opening or closing. Stale refs were the single largest error category in a measured run (9 of 19 errors, all in the survey phase, all from clicking on with refs taken several turns earlier). The rule: **before acting on any element, the ref you pass was returned by a read performed AFTER the last page-changing action.** Never reuse a ref across a page change, however recently it was taken, and never "re-derive" one from memory. Re-acquire it with a scoped read (below), not a full snapshot.

**Read only what changed.** Snapshot + click were ~49% of every authoring call and ~76% of survey-phase calls in the measured run. Most actions only need one thing confirmed — the field you filled, the row that appeared, the dialog that opened. The read ladder, strict:

1. `browser_find` (or the scoped snapshot form) on the ONE region the next action or check needs — the default after every action, and the only sanctioned way to refresh a ref.
2. `browser_evaluate` returning trimmed data (attributes, counts, short text; arrays `.slice(0, 20)`) — for hooks, counts, and values; it returns no refs, so it never precedes a click on its own.
3. Full `browser_snapshot` — only on the first arrival at a surface you have not mapped this session (a genuine navigation to new territory). A second full snapshot of a surface you already mapped is a defect: after a click, read the region the click changed, not the tree.

The rulebook's chaining discipline is unchanged: the action and the scoped read of its effect belong in the same turn, and the turn ends on the read the next decision needs.

**Save or discard before leaving a dirty surface — walk AND authored steps.** A schema tab, settings tab, or create/edit form with pending edits blocks navigation with a native `beforeunload` dialog. In the walk that turned a five-second navigation into a full minute of timeout; in a compiled run it hangs the gate, because the step grammar has no dialog handling. The rule, both places:

- **Before any navigation away from a surface where you changed a value** — a `navigate`, a `go_back`, a click on a nav item, tab, breadcrumb, or Back — the pending change is committed or discarded through the app's own control first: `Save` when the scenario wants the change kept (readiness pair follows — it refetches); the surface's `Cancel` / `Discard` / `Reset` / page-level `Back` when it does not. Whichever you performed in the walk is the step you author; the walk decides, per surface (rulebook: _Commit semantics are per-action_).
- **Authored steps:** a payload that leaves a dirty surface by navigation with no save/discard step before it is a defect — pre-flight check 8: for every navigation step, name the earlier save/discard that cleared the surface, or confirm no value was changed on it since arrival. A scenario whose stated behavior IS the discard ("Back discards the draft") already satisfies this — the Back click is the discard.
- **In the walk, if the native dialog appears anyway** (you missed a pending change): dismiss it with `browser_handle_dialog` (dismiss/cancel — never accept a "leave without saving" prompt during the survey, which silently drops your edits), then commit or discard via the app control, then navigate. Record the surface as dirty-blocking in your scratch note so the authored steps carry the save/discard.

**Provision the minimum; split by behavior.** Correctness is the goal, and long payloads fail for authoring reasons — more steps to get wrong, more surfaces to leave dirty, more refs to go stale. A scenario provisions exactly the records its stated behavior needs and nothing more (search: one record; sort: two; filter: one per property value asserted). A scenario that would exceed **40 steps**, or that exercises more than one behavior on the records it creates, is split into separate test cases in `scenarios.md` before authoring — each self-provisioning its own data (test cases never share records). The readiness pair is never what gets trimmed (_The readiness pair is unconditional_).

## Phase 1 — Explore the app and propose scenarios

Goal: a reviewed list of test scenarios that describe **behaviors this app actually has**, each one testable and independent, and together covering **every behaviour the survey saw** (step 4). Never invent a scenario for a feature you did not see working, and never leave out one you did.

**Survey file.** As you survey, write what you learn on each surface to its own survey file, `.sessions/<sessionId>/test-author/survey-<k>.md` in the working folder; each approved scenario's run-file entry names its surface's file (`parallel-authoring.md`, _The run file_). Each authoring helper starts from that file in a browser that has seen nothing, so put first the **traps for authors**: whatever a fresh walk would trip on, such as two fields sharing an id, a hidden or decoy copy of a control, a form that changes shape with a choice, an input's required format, a picker that takes only a folder, a menu that opens elsewhere on the page, a control that looks live but does nothing, a dialog with no close. Then the surface's purpose, its interactive inventory with the durable hooks found, and its creation paths and what they need. **Number every inventory item** (`S<k>.<n>`: `S2.7` is the seventh item of surface 2), one id per behaviour a test could check: a control and what it does, a column with its sort and filter, a form field with its validation, a tab, a state, a number another number must agree with. The coverage check (step 4) ticks the scenarios against these ids, so an item with no id is an item nothing accounts for.

**1. Survey, don't test.** Open the app's root URL (`browser_navigate`), then map it: take a snapshot of the landing page, walk the primary navigation, and visit each main surface once. A login wall is handled by the test-user sign-in flow (SKILL.md, _Sign in as a test user_): run it — never ask me to sign in with my own account — and once signed in, resolve the user id (_Resolving the user id_, below); never ask me for it or for an applicationId. On each surface record — in a scratch note, not yet as scenarios — the page URL, its purpose in one line, and its **interactive inventory**: tables/lists (with their columns, sort/filter/search/pagination controls), forms and their fields, toggles and view switches, tabs, KPI/summary cards, detail links, action buttons, and any obvious relationships between numbers on screen. Prefer reading (one full `browser_snapshot` on first arrival, then `browser_find` / `browser_evaluate` for everything else — _Walk discipline_) over clicking during the survey; where a control's effect is not obvious, click it once, read the region it changed with a scoped read, and go back — with a fresh ref for the Back, never one from before the click. Keep the survey to a few minutes per surface — depth comes later, per scenario.


**2. Do not touch, in either phase:** anything that emails, pays, deletes, or mutates records you did not create; destructive bulk actions; account/security settings; another user's data. If a surface is behind such an action, note it as out of scope. **This rule protects other people's data — it never excuses a scenario from creating its own.** During the survey, walk each creation path once (create a throwaway random-named record, observe the form's required fields and the record's landing page, delete it if the app allows) — that walk is what tells you which features are self-provisionable.

**3. Turn the inventory into candidate scenarios.** A scenario earns a place only if ALL of these hold:
- **It describes observed behavior**, not a feature you assume exists.
- **It has a stated, checkable outcome** — say what must be true afterwards, in the scenario text itself. "Search the candidates table" is not a scenario; "Searching the candidates table for a term filters the rows to matches and shows the term in the search box" is.
- **It is one behavior**, not a tour. Prefer several small scenarios to one long journey.
- **It is independent** — starts from a URL, assumes no other test ran first, leaves the app usable for the next test.
- **It is self-provisioning (HARD RULE — _Self-provisioning_, above).** The scenario text names the records it creates and every outcome is stated about those records. No existing record by name, no witness of membership, no "fewer rows than before", no observed count, no shared view/tag. Litmus: delete every record the test did not create — is the scenario still provable? If a behavior can only be described using data the test cannot create, it goes to "not covered" with that reason; it is never proposed as "fragile".
- **It is about the network only when the app is.** Propose a scenario that needs a network rule or goes offline (`network-rules.md`) only when the person or the scenario names an error from the server, a slow load or being offline, or the survey saw the app's own UI for one (an error message, a retry button, a loader, an offline banner). Its entry names the call the rule acts on and what happens to it, or where the user goes offline, so the person sees it at approval.
- **It names every person it needs.** A behavior that involves another person (`multi-user.md`) is a scenario with more than one person. Its text names each role and what each one does and sees, the first role always being the signed-in test user. A role keeps one name in every scenario it appears in, because the approval asks once per role name which test user plays it. Propose it only when the survey saw the first person's side (the send control, the assignee picker, the link to an approval queue); the helper walks the other side, and a walk that contradicts it follows the scenario–observation conflict protocol (`local-rules.md`), whose question also offers another test user for that role (`multi-user.md`). A public app signs no one in, so a scenario with more than one person there goes to "not covered".
- **It is expressible in the step grammar below.** Behaviors needing native dialogs or new tabs belong in the "not covered" list, with the reason — as does a check on a downloaded file the grammar cannot read (_Download a file_ in `local-rules.md`: the text of a scanned PDF, a file inside a zip, more than one file from one action, a docx page count, any xlsx sheet but the first, a download made inside an extension side panel), and any feature whose data the test cannot create (system-defined entities, a read-only role).
- **It says what the app does not control (`durability.md`).** A scenario whose stated outcome is a model's decision ends with the line `AI-dependent: <what the model decides>`, and needs at most three model replies; one that changes state every case of the user sees (a pin, a toggle, a setting) names the restore and is marked `shared state`, so it is dispatched alone. A behaviour that needs more replies than the run's time budget allows, or a generation the survey measured over two minutes, goes to "not covered" with `not expressible: exceeds the run time budget`.

**4. Cover every behaviour the survey saw (HARD RULE; the default scope).** The scenarios cover the app as it is, not a sample of it: every inventory id of every survey file ends in exactly one place, a scenario that exercises it or a row of "not covered, and why" with one of the fixed reasons below. The person never has to come back and ask for the rest. Nothing is left out because the list is long, the person named no area, the survey took long or a surface looks minor. Breadth and depth are both owed: every surface, and on each surface every category it has: navigation and landing state · table/list behavior (sort, filter, search, pagination, row actions, empty/edge states — each exercised on records the scenario creates, isolated by identity or shared random prefix) · view/mode switches and tabs · forms (happy path, required-field validation, cancel/reset) · detail views reached from a list and the return path · cross-checks between displayed numbers (a KPI vs. the rows it summarizes, totals that should add up) · state that must persist across a navigation. Cross-check scenarios are the highest-value ones in most apps — they catch real bugs — and they are only legitimate when the test creates the entity whose numbers are compared, so both sides are test-controlled. A scenario covers one id (a create form's happy path is one id; each field's validation is its own), and one id may need several scenarios (a table's sort and its filter); a scenario tests one behavior.

**The fixed "not covered" reasons.** Each row names the inventory ids it accounts for and starts with one of: `requires pre-existing data; no creation path` (_Self-provisioning_) · `out of scope: <emails | pays | deletes others' data | account or security settings>` (step 2) · `not expressible: <native dialog | file download | …>` · `needs another person on a public app` · `could not reach: <what stopped the walk>` · `outside the cap or the named areas` (below) · `covered by existing case <name>` (a reconcile run only). "Low value", "minor" or "similar to another scenario" is never a reason: a behaviour that is minor still gets its scenario.

**The coverage check, before `scenarios.md` is written.** Walk every survey file's inventory ids in order and tick each against the scenarios and the not-covered rows. An id in neither gets its scenario now, or its row with a reason. Then write the `## Coverage` table of `scenarios.md`: one row per surface (surface · ids · in a scenario · not covered), a totals row, and under it one line, `Coverage: <in a scenario> of <ids> behaviours have a scenario; <not covered> not covered, each with a reason.` Each scenario entry lists the ids it covers, so the table can be checked against the entries. The approval message quotes the Coverage line. A table that does not add up to the ids the survey files hold is not written: find the ids it lost.

**A cap or named areas narrow what is proposed, never what is accounted for.** When the person gives a cap, propose that many, best-first; when they name areas, propose those areas' scenarios. Every other inventory id goes under `outside the cap or the named areas`, so the person sees what a later run can still take. Never set a cap or pick areas of your own, and never ask whether to propose more: proposing everything is the default.

**5. Write `scenarios.md` inside the run folder (`tests/<slug>/` in the working folder, created first — never flat in the working folder; SKILL.md, Phase 1) and STOP.** Format: a numbered list, each entry with a **title** (≤ 8 words), the **scenario text** (2–4 sentences, written as an instruction to a test author, including the stated outcome and the starting URL), the **surface** it lives on, a **priority** (P1 core behavior / P2 useful / P3 nice-to-have), and for a scenario with more than one person its **roles** in order. Add the `## Coverage` table and the "not covered, and why" section, every row with a fixed reason and the ids it accounts for (step 4). Then report: the Coverage line, how many scenarios, the surfaces covered, which creation paths each relies on, any risks (flaky-looking areas, things you couldn't reach). "Data-dependence" is never a reported risk — a scenario carrying one is rewritten or moved to "not covered" before the file is written. **Wait for my approval or edits before authoring anything.** A cap or named areas from me follow step 4: that many, best-first, or those areas proposed, and every other id accounted for as `outside the cap or the named areas`.


## Reading a failed submission — the failure table (fix round)

At submission, `deliver_steps` runs the case through: candidate generation from your locators → id-hook check → element resolution and creation → compile → a live green-gate run → save. Success is a result carrying `publishStepsResult.testCaseId` and no `errorAt`; a stopped run names its stage in `errorAt` beside that stage's evidence, and a call that failed outside any stage comes back `isError` with a plain message (submission contract, _Reading the response_). "gate:" rows below are `errorAt` `Green Gate` read from `greenGateResult.run` (`output`, `error`, `exitCode`) — a red test always comes back that way, because the spec runner returns its run rather than failing its own workflow. Fix the STEPS, never the check: a verification the scenario asked for that cannot hold is a finding to report in `observations`, not an assertion to soften or delete. Fix every occurrence of a cause across the payload, not only the step the message names — the same authoring mistake repeats across sibling steps built the same way. When a message maps to nothing below, re-open the app and look at the actual page state at that step before changing anything.

**What the failures mean:**

| response | cause | fix |
|---|---|---|
| `errorAt` `Generate Element Candidates (MCP)` with `metadata.message` naming the element (e.g. `[unmappable_locator] Save`) | a locator link outside the closed vocabulary; the message names the element and what does not map | rewrite that link in a mappable form: `.nth()`/`.first()`/`.last()` → `:scope > :nth-child(n)` under its anchored parent; `.frameLocator()` → move it to the front of the chain, outermost frame first, with the element after it; `.filter()` → re-anchor to an attribute/role/label; tag+attribute in one link → split into two; `#id` with dots → `[id="…"]`; class selector → forbidden, find a real hook |
| `errorAt` `Convert Steps To Script` with `violations` (each `message` names a step path and says it carries generated/record id(s)) | a machine/record id rode in as a hook (hex run, UUID, `e_…`, `_r_…`) or in an element name | anchor on the container's static hook and position the item with a slot link; strip record ids from names |
| `errorAt` `Convert Steps To Script` with `metadata.message` `step <id>: user "<x>" is not one of this test's users (<names>).` or `test user "<name>" is added to this test twice.` | an argument defect, not a step defect: a step's `user` is not in `userIds`, or `userIds` repeats an id | fix the ARGUMENTS against the submission contract: `userIds` is the entry's `userIds` from the run file, and every step's `user` is one of them (`multi-user.md`); resubmit with the steps otherwise untouched |
| `errorAt` `Green Gate` with `metadata.message` `a non-public run mints a session per test user — pass the userIds to run as` | an argument defect, not infrastructure: the app is private and the submission carried no test user (`userIds` empty) | fix the ARGUMENTS against the submission contract and resubmit. An empty `users` in the run file means the run took a private app for public: stop and tell the user, since the run needs the test-user sign-in first |
| `errorAt` `Convert Steps To Script` with `metadata.message`: a compile error naming a step/field | the step violates the grammar — unknown action or assertion type, a state used as a type (`{"type":"visible"}` instead of `element_state`), an assertion with no valid `type`, an inline `selector` nested inside `element` (it is a step-level field) | correct the field against the grammar above; if no typed shape fits, use `execute_js_verify` or move the check to `"excluded"` |
| `errorAt` `Convert Steps To Script` with `metadata.message` naming an `api_request` field — a missing/unknown `method`, a `body` that is not a string or does not parse as JSON once tokens are stubbed, a header row with a blank or illegal `key`, a `saves` row with an illegal `into` or a `path` that is not dot/bracket syntax, two `saves` rows sharing one `into`, or a `stored_value` assertion naming a variable nothing in the test saves | the step violates `api-requests.md`'s grammar — never a run-time surprise | fix the named field against `api-requests.md`; a `stored_value` naming the wrong variable gets the message's own list of names the test actually saves — pick from it, never guess |
| gate: an `api_request` step fails with the response body (truncated) in the error, a 401 showing the server's `www-authenticate` header | the call returned a non-2xx status; by design there is no `expectStatus` field, so any non-2xx always fails the step | not a step defect when the scenario expected success: fix what the call sends (the address, a header, the body) against the curl/description it was built from; a scenario that needs to assert a call FAILS is out of scope today — move it to `excluded` rather than inventing a field |
| gate: `This environment's Test Studio kit has no httpKit: a deploy has to publish the current kit before this test can run.` | the tenant's published test-kit bundle predates `httpKit` | infrastructure, not a step defect: tell the person the environment needs a kit deploy; never rewrite the step to work around it |
| `errorAt` `Convert Steps To Script` naming a download rule: `No earlier step waits for a download, so this check has no file to read…`, `No earlier step by <name> waits for a download…`, `The last step before this one that waits for a download is inside an if or loop…`, `Check the downloaded file in a step after the one that downloads it.`, `Only a step that acts can wait for a download…`, `Click the link that downloads the file…`, `A file downloaded inside an extension side panel cannot be checked…`, `Check the downloaded file on the page, not in an extension.`, `The match "<m>" is not one of …`, `The size unit "<u>" is not one of KB, MB.` | the steps break the download order (_Downloads_, `local-rules.md`) | mark the acting step that downloads, before the check; `No earlier step by <name>`: each user reads only their own downloads, so the check takes the `user` of the step that downloaded, or that user's own download is marked; `… inside an if or loop …`: move the check into that body, after its marked step (inside a loop, also when the check sits before the body's own download), or mark a download outside it before the check — never mark an extra step only to silence it; a check on the marked step moves to its own later `assert`; mark the link's click, never the navigation or the `if`; a check drops `surface`, and a side-panel download goes to `excluded`; a refused `match`: `download_name` takes `exact` \| `contains` \| `not_contains`, `download_text` `contains` \| `not_contains` |
| `errorAt` `Convert Steps To Script` on a `wait_for_download`: `Put "Wait for the download" right after the step that downloads the file…`, `Going to a URL cannot download a file…`, `An if or a loop cannot download a file itself…`, `The step before this one already waits for a download.`, `<A> cannot wait for a file <B> downloads…` | a saved case's `wait_for_download` does not sit right after the same user's acting step that downloads | move the wait right after that step, at the same level, with the same `user`; after a marked step, delete the wait (the mark already waits); in an `if`/loop, the wait goes inside, after the acting step |
| gate: click timeout after a `fill` on a freshly navigated page — log shows "element was detached from the DOM, retrying" and/or the submit resolving as `disabled`/"not enabled" | the fill landed on the pre-hydration input; the client re-mounted the form and dropped the value — the readiness pair is missing after the preceding `navigate`/`navigatesTo` click (_The readiness pair is unconditional_) | insert the pair (settle + `wait` 2) directly after the navigation, before the first fill; apply to every navigation in the payload, not only the one the error names |
| gate: timeout on a `navigate`/`go_back`/nav click that follows an edit on a schema, settings, or create/edit surface with no `Save`/`Cancel`/`Discard` step between | the surface was left dirty; the app raised a native leave-page dialog the grammar cannot answer (_Walk discipline_, Save or discard) | re-walk the surface; author the save (with readiness pair) or the app's discard control before the navigation — whichever the scenario means |
| gate: "element not found" / timeout on a click | the element isn't there at that point in the flow — usually a missing navigation/opening step, a stale scope, or a missing readiness pair before a read | walk that point again in the browser; add the missing step or the pair; never just re-run hoping |
| gate: strict-mode violation (multiple matches) | the locator resolves to more than one node | inspect the extras (`browser_evaluate` → `outerHTML`); `aria-hidden`/`readonly` decoys → switch to a role/label link; genuinely distinct → add a scoping parent link. Never resolve it with a positional tail |
| gate: assertion failed, but the page visibly satisfies it | most often a hardcoded value that drifted, a substring trap (`'Available'` inside `'Unavailable'`), a double-escaped regex in JS (`\\s` where `\s` was meant), or an assert reading the pre-refresh state | re-check the literal's license, the escaping, and whether a readiness pair is missing before the read |
| gate: assertion failed on a named row / count / "fewer than" relation, or "element not found" for a record the steps never created | the scenario is data-dependent — a record, count, view, or ordering that belongs to the tenant's current data, not to the test | not a step fix: rewrite the scenario as create → act → verify (_Self-provisioning_), re-walk it, and author the creation steps; if nothing can create that data, move it to "not covered" |
| `execute_js_verify` returns false while the page looks right | the predicate is wrong, not the app: doubled escapes, a probe over a text blob instead of the component's own element, or a sweep reconciled against itself | dry-run the source again via `browser_evaluate` at that exact state and fix what it actually returns |
| gate: `This step did not download a file.` on the step marked `downloads: true`, `No file was downloaded by the step before this one.` on a `wait_for_download`, or `No file has been downloaded yet: the step that downloads it has not run.` on a check | no new file reached that user's browser within 30 s of the step's action: the control opens a menu or dialog first, the file comes later from a notification or link, or the run's user may not download there — or the marked step sits in an `if` or loop that did not run | walk that step again as the same user and read its `Downloaded file` event; mark the step that does download (the menu item, the notification's link) and keep the check in the same branch as it; never add a `wait`. A download the walk sees but the run never gets is a finding: report it in `observations` |
| gate: `The downloaded <name> is not a real .<ext> file: the app served something else under its name, such as an error or sign-in page.` or `… is password-protected (an encrypted Office file) …` | the step downloaded a web page under the file's name — a sign-in, error or permission page — or a password-locked Office file, so every check on that file fails, whichever runs first | open the file the walk saved (the path in its `Downloaded file` event). A real file there means the test user is not allowed or not signed in where the walk was: report it in `observations` as a finding and keep every check. An HTML page there too means the step acts on the wrong control: walk to the one that downloads the file. A password-locked file, or a real `.csv`/`.tsv` whose very first cell starts like a tag (`<NA>`, `<blank>`): every check on it goes to `excluded` with that reason |
| gate: `The downloaded <name> has no text a test can read: …`, `… has formulas with no saved result (first at <cell>) …`, `… has rows holding only formulas with no saved result (first at <cell>) …`, `… is password-protected, so a test cannot read it.`, or `A .<ext> file has no rows to count: only .xlsx, .csv and .tsv files do.` / `… no pages to count: only .pdf and .pptx files do.` | the reader gets no text, rows or pages from this file: a scanned or drawn PDF, a docx or pptx holding only pictures, charts, SmartArt or headers and footers, a file that is not text (.zip, image, old .xls, UTF-16 with no byte-order mark), an xlsx with unsaved formulas (its text; its rows too when a row holds only such formulas), a password-protected PDF — or a count on a type that has none | keep what still checks (name, type, size; a readable PDF's pages) and move each text, row, page and text-store check the message names to `excluded` with its reason, never to a weaker check |
| gate: `The downloaded <name> could not be read as a .<ext> file: <reason>.`, then `Reader said: "…"` or `It may have been cut off, …` | the file the app served is damaged, cut off or another format under its name; the reader refused it instead of reading wrong content. Its name, type and size still check | a finding about the file: report it in `observations` with the message and keep every check — never loosen or drop one to reach green. `Extension <name> could not be unpacked: …` is the same for an extension's build: report it, so the main session asks the person for the build again |
| gate: `The test runner cannot read .<ext> files: …` | the runner lacks, or cannot load, the package that reads that file type (xlsx, docx, pdf) — the platform's setup, not your steps | do not rewrite or weaken any step: stop submitting the cases that read that type's content, tell the user the package the message names, and mark those cases `authored, not submitted`; other cases continue |
| gate: `Cannot read properties of undefined (reading '<member>')` on a `downloadKit.<member>` call, or `downloadKit.<member> is not a function` | the runner's test kit predates download checks (the spec reads `downloadKit` from the runner's `uaTestKit`) — the platform's setup, not your steps | same as the row above: stop submitting cases that download, tell the user the runner's test kit needs updating, mark them `authored, not submitted` |
| gate: `Cannot find module '…/ua-test-kit.js'`, then `No tests found` | the runner did not put its test kit beside the spec, so no case runs there, download or not — the platform's setup, not your steps | do not rewrite or weaken any step: stop submitting every case, tell the user the runner on this tenant is missing its test kit (`ua-test-kit.js`), mark each remaining case `authored, not submitted` and keep its payload to deliver unchanged once the kit is back |
| gate: a `download_name` check `Expected: "<X>"` / `Received: "<name>"`; `The downloaded <name> does not contain "<X>" …. Text in an xlsx, docx, pptx or tsv (the message adds "inside one cell or across whole cells"): `X` starts or ends partway through a cell, joins parts of two cells, or mixes an xlsx cell's shown and stored forms — a stored page row fails when the file shows one of its cells differently (a date). A PDF whose `Its text starts:` does not spell the page's words: the reader cannot decode its font. Cells: the value exactly as its cell shows it in the saved file, or one check per cell; a stored `<<var>>` stores the whole cell or row. An unreadable PDF: its text checks to `excluded` with that reason. A failed `not_contains`: a value the file really holds is a finding, never a check to loosen; one that arises only by joining needs a value that cannot (a longer, more distinctive one) |
| `errorAt` `Generate Element Candidates (MCP)`, no message | the stage produced nothing for these steps; no locator is named | resubmit the same case unchanged once; if it repeats, report it with the error. Never guess which locator to rewrite |
| `errorAt` `Green Gate` with any other `metadata.message` only and **no** `greenGateResult` | the gate CALL itself failed, so no run happened — not a verdict on your steps. Never rewrite steps for it — there is no run output to rewrite them against |
| `errorAt` `Replace Elements With Ids (MCP)`, no message | an element the steps carry did not resolve to a stored element id on the platform side. | `isError`, a message about the call itself: `nothing to publish to`, `cannot publish a new test case without the asset`, `no platform to call`, a rejected `host` | a missing or malformed argument, not a step defect | fix the ARGUMENTS against the submission contract (`name`, `interfaceId`, `host`) and resubmit; the steps are untouched |
| `errorAt` `Convert Steps To Script` with `metadata.message` lines under `The case's saved network rules fail:` | a rule saved on the re-delivered case, not one you sent, is on and incomplete (a maker's half-written rule), so the compile stops on it | never edit, disable or drop it, and never resend the list to get past it: stop and report `needs_answer` quoting those lines, for the person to fix the rule in the case's Network tab |

| gate: an assert after the rule should have acted fails, and the run shows the app behaving as if no rule were on (no error, no loader, the record saved) | the rule never acted; the run output names it on a line starting `network rule "` | do what `network-rules.md`, _A rule that never acted_, says |
| gate: an assert after `go_offline` or `go_online` fails on a change the app makes on its own timer (presence, a retry, a reconnect) | the `wait` before it is missing, or shorter than the timer in the run | re-measure the timer and set the `wait` as `network-rules.md`, _Waiting on the app's own timer_, says |
| `errorAt` `Green Gate` with `metadata.message` naming `No platform_automation record for type` `RUN_PLAYWRIGHT_SPEC` or `TEST_STUDIO_MINT_SESSION` | the tenant lacks a callable automation the green gate runs through; tenant setup, not your steps, and not transient | stop submitting; tell the user which type is missing, and mark each finished case `authored, not submitted` |
| `errorAt` `Publish Steps` with `metadata.message` | the test passed the green gate but the save failed | do not rewrite steps; resubmit the same case unchanged once (there is no publish-only call, so the gate runs again); if it repeats, record the message and tell the user |
| transport / infra error — `isError` with a timeout, unreachable host, or 5xx; an HTTP 5xx or empty body from the endpoint; `errorAt` `Green Gate` whose `metadata.message` is a session-mint, network or timeout failure (the run could not start); or `DEADLINE_EXCEEDED` / "route ... service in fail-fast" naming a `scripts-playwright` (or other backend) service, especially when **every** submission of a session carries the same message | the platform's run service failed or timed out, not your steps | do not rewrite steps — the payload is fine; wait for the service to recover and **resubmit the same case unchanged** (the submission contract), retrying once; if it persists, stop and tell the user it is a platform-side outage |

When a scenario goes green, record it as created, with its `testCaseId`, in the run's ledger (`scenarios.md`, or `results.md` for scenarios from another source) and note the number of submission attempts it took in your summary. When one refuses to go green, record it in the ledger with the error and what you tried, and continue with the next.
