# Submission contract — one `deliver_steps` call per test case

Each authored test case is created by one `deliver_steps` call on the
`app-testing` server. The bridge sends it to the **platform host** the UnifyApps Headless
session is signed in to — the origin of the run's platform screen URL (run
header in the run's ledger), never the matrix domain — with the session cookie
attached (`platform-tools.md`, _The session cookie_). One call runs the whole
pipeline: candidate generation from your locators → id-hook check → element
resolution and creation → compile → a live green-gate run → save. Nothing is
saved unless the green gate passed. Build and check the steps in the scenario's own payload file,
`<run-folder>/payloads/<key>.json` (helpers submit side by side, so a shared
file would be overwritten). The main session deletes `payloads/` after the
run's last submission; the run's ledger, `scenarios.md` or `results.md`
(`parallel-authoring.md`), is the run folder's durable artifact.

## Before the first submission

The `app-testing` tool list (`platform-tools.md`, _Availability_) MUST
include `deliver_steps`. The main session checks it once per run, before the
first helper is dispatched; a helper never checks, and takes the outcome from
the run file's `submit` (`parallel-authoring.md`, _The run file_). If it does
not list `deliver_steps`, the tenant's platform predates this contract: tell
the person once, keep authoring with `submit` set to `false`, and mark each
finished case `authored, not submitted` in the run's ledger.

## The call

One `deliver_steps` call per case, carrying the arguments below and nothing
else; load the tool first with one ToolSearch (`select:` with its full
`mcp__plugin_ua_app-testing__…` name). The bridge adds the cookie and the 450-second deadline (the green-gate
run alone may take 300); there is no envelope, host header or timeout for you
to write.

## The arguments

One test case per call:

| argument | content |
|---|---|
| `host` | `https://<platform-host>`, always sent; the tool falls back to the request's `Origin` header only when it is missing |
| `ifExists` | the literal `"update"`, on every call that sends no `testCaseId`: a case of this exact `name` already on the app is re-delivered in place instead of a second one created, so a resubmission can never file a duplicate |
| `name` | the test case name, generated by you: 4–6 words, sentence case, action-first, derived from the entry's title ("Create ticket and verify dashboard", "Switch candidates list to grid"), unique within the run. Required: without it the call is refused |
| `module` | the `## <Module>` heading this test case sits under in `scenarios.md` (or, for scenarios from another source, the module the run file's entry names). For an app it is the app's display name from the platform, the one module of the run; for a test of the platform itself it is the product area the case exercises, named as the platform's own navigation names it ("Solution Builder", "Automations", "Test Studio", "Settings"), 1–3 words. **Verbatim-identical across every test case of that module** (the platform finds or creates the module by string equality, then the feature inside it). Always sent for a new case |
| `feature` | the `### <Feature>` heading this test case sits under, inside its module (or the run file entry's `feature`), lower-case `feature` as the tool declares it; 2–3 words, **verbatim-identical across every test case of that feature** (the platform finds or creates the feature inside the module by string equality) |
| `scenario` | the `#### <Scenario>` group heading (or the run file entry's `scenarioGroup`), 2–3 words, same verbatim-identity rule. It also titles the compiled test and labels its green-gate run |
| `description` | the entire scenario text the user saw and approved: the numbered entry's full text from `scenarios.md` (the 2–4 sentences with the stated outcome and starting URL), or the scenario's full text from the source the person gave, verbatim as it stood after the Phase 1 approval including any edits the user made, never a paraphrase, summary or the title. The platform stores it on the case as its durable statement of intent; the auto-heal run reads it back and validates the implemented steps against it |
| `url` | the starting page URL; the green gate also scopes the test user's session cookie to it |
| `extensions` | only when the scenario entry has `extensions`: that list from the run file, verbatim — never `panelApps`. Omitted otherwise; a re-delivery that omits it keeps the case's own |
| `device` | `{ "type", "variant" }` of the device the walk ran as: the entry's `device` when it has one, else the run file's ([devices-and-browsers.md](devices-and-browsers.md), _Submitting_), e.g. `{ "type": "tablet", "variant": "ipadMiniH" }`. Never its `userAgent`, `isMobile` or `hasTouch`: the model gives the size and the type the emulation. Omitted when the run file's `device` is `null` and when the subject is the platform. Never send `viewport` |
| `networkRules` | only when the payload has rules: the payload's `networkRules`, verbatim and in order. Omitted otherwise; never `[]` or `null`. Sending it **replaces the case's whole list**, so on a re-delivery (`testCaseId`) leave it out to keep the case's own rules, which the run then compiles; send it only when the scenario changes them, and then as every rule `get_test_case`'s `properties.networkRules` holds, unchanged and in order (ids and `disabled` included), with yours added or edited. Leave out an entry `networkRulesWarning` names: it stays saved where it is |
| `userIds` | the scenario entry's `userIds` from the run file, verbatim: the test users the case runs as, in order, the first the default, e.g. `["110495", "110496"]`. **For a public app, send `[]`** (never a blank, `null` or placeholder id inside it) |
| `steps` | the authored steps array, exactly the `steps` from the payload the rulebook has you build, never empty; `observations` and `excluded` are **not** sent — they stay in the report and `scenarios.md` notes. A step carries `user`, which picks the one of `userIds` that performs it, only as [multi-user.md](multi-user.md) says; with one id in `userIds`, no step carries it |
| `interfaceId` | the deployed interface's id, resolved **once per run** by the main session with a read-only `GET /auth/interface/deployed` on the app-under-test's own origin (a `browser_evaluate` `fetch` with `credentials: 'include'`, the same pattern as the user-context call). Record it in the run header of `scenarios.md` and in the run file (`parallel-authoring.md`, _The run file_), where every helper reads it, and reuse it for every case. If the call fails or returns no id, stop and tell the user; never guess one, scrape one from the UI, or ask for one. **When the detected subject is the platform itself**, send the literal `"__UA__PLATFORM__"` instead and make no deployed-interface GET: it is the key the platform files platform-owned elements and cases under |
| `assetClass` | the literal `"e_interface"` |

**Never send `testCaseId` when authoring a new case**: given one, the tool
re-delivers that existing case in place instead of creating a new one. The
one job that sends it is the heal loop's update job (`agents/test-author-agent.md`,
_Update_): there `testCaseId` is the entry's `caseId`, `name`, `module`,
`feature`, `scenario`, `description` and `userIds` are the case's own, word
for word (a case saved before modules has none: leave `module` out),
and the green gate proves the re-authored steps before they replace the
stored ones. Never send `datasetId`,
`rowReference` or `rowSelectionMode` (no dataset binding locally), or
`caseId` (a Service Hub case, which a local run never has).

## Reading the response

The result is one text content item holding JSON (`platform-tools.md`,
_Result_). It repeats the steps and the compiled script, so read the fields
below; never print it whole.

- **The bridge refuses the call** with `AUTH_EXPIRED` (the session lapsed) or
  `NOT_STARTED` (no UnifyApps Headless session in this folder): the main session loads the
  `setup` skill, which signs in again, then retry once.
- **`isError: true`**: the call failed outside any stage; the text is a plain
  message, not JSON. A message about the call itself (`nothing to publish
  to`, `cannot publish a new test case without the asset`, `no platform to
  call`, a rejected `host`) is a wrong argument: fix the ARGUMENTS against the
  table above and resubmit. A timeout, an unreachable host or a 5xx is
  infrastructure.
- **Otherwise the text is one JSON object.** Parse it.
  - **No `errorAt`, and `publishStepsResult.testCaseId` is present**: success.
    The case compiled, passed the green gate live, and was saved, filed
    under `publishStepsResult.moduleId`, `featureId` and `scenarioId`. Record the
    `testCaseId` and the attempt count against the entry in the run's ledger.
    `greenGateResult.run.output` holds the Playwright run log (e.g.
    `1 passed (12.7s)`). **A line in it starting `network rule "` means a
    rule never acted**: the case is saved but tests nothing about that rule.
    Do what `network-rules.md`, _A rule that never acted_, says, then report
    `created` with a note quoting the warning and what the walk showed, for
    the person to fix in the case's Network tab in Test Studio.
  - **`networkRulesWarning`**, on success or beside an `errorAt`: the case
    holds saved rules this version cannot read. The run went without them
    and they stay saved on the case where they are. Never resend to clear
    it, and never copy those entries into `networkRules`; quote it in the
    entry's `notes` for the person.
  - **`errorAt` is present**: the stage that stopped the run; nothing was
    saved. Map it through the failure table in `local-adaptations.md`, using
    the evidence that stage returns:

| `errorAt` | evidence beside it |
|---|---|
| `Generate Element Candidates (MCP)` | `metadata.message`, naming the element whose locator does not map and why (e.g. `[unmappable_locator] Save`); none when the stage produced nothing |
| `Convert Steps To Script` | `violations` (the id-hook gate; each `message` names the step path and the id) or `metadata.message` (a compile error) |
| `Replace Elements With Ids (MCP)` | none; an element did not resolve to a stored id |
| `Green Gate` | `greenGateResult.run` (`output`, `error`, `exitCode`) — a red test always comes back this way, because the spec runner returns its run rather than failing its own workflow. `metadata.message` alone, with no `greenGateResult`, means the gate CALL failed and no run happened: infrastructure, not a verdict on the steps, except `USER_REQUIRED`'s message (the failure table) |
| `Publish Steps` | `metadata.message`; the test passed but the save failed |

- **`Tenant MCP returned HTTP 5xx`, an empty result, or a network or timeout
  error from the bridge** (the call could not be sent, or 450 seconds ran
  out): infrastructure, never a reason to rewrite steps. The server may still
  have finished and saved the case (a 504 often means exactly that). Before
  resubmitting, call `fetch_test_cases` with the case's `name` as `name` and
  look for a row whose name equals it exactly: if there is one, record it as
  created with that id. Otherwise resubmit the same case unchanged, with
  `ifExists: "update"` as always, once the service recovers.
- **More than one test case is called** the case's name (the call stops
  before its run and names both ids): record the case as failed with that
  message; never resubmit it under another name to get past it.
