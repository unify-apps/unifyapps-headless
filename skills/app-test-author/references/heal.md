# Heal — failed executions to locator patches

Loaded by SKILL.md's heal run. Scope: test cases whose executions failed because a **locator no longer resolves — or resolves to a different element than the one the step means** — find the intended element in the live app, patch that one element's `locator`/`name`, and prove the whole case green. Everything here rides the existing doctrine **by reference**: walk discipline, the readiness pair, and the failure table (`references/local-adaptations.md`); the locator rules and vocabulary (`references/local-rules.md`, _Locator rules_); the durability ladder of the dialect file the detection picked; and the platform tools' calling convention, session cookie, and availability probe (`references/platform-tools.md` — every `url` argument below is the platform screen URL, and a tool missing from the probe stops the mode, per that file).

**Invariants (HARD — what a heal may touch).** A heal changes ONLY the `locator` and `name` of the element (or sanctioned inline `selector`) the failing step targets. It MUST NOT change any step's action, `value`, assertions or `user`; MUST NOT add, remove, or reorder steps; MUST NOT add waits or retries; MUST NOT loosen or rewrite an assertion to reach green. A red that needs any of those is not a heal — it is reported (fix-round or update-run territory).

## Entry

**A. No case named (the default).**

1. `fetch_failed_executions` (`url`, `limit?`) — the failed runs, newest first.
2. **Dedupe before any detail call:** using the test case id on each execution, keep only the most recent failed execution per test case — older failures of the same case are dropped here so they cost no reason fetches. A failure on the deployed app wins over a newer one on a branch preview (its `DOMAIN`; `platform-tools.md`, _Running on another domain_): the heal works on the deployed app, and a preview's red belongs to the pull request. A case whose only failures are on a preview goes to the summary's skipped list, reason `ran on <host>, a branch preview`.
3. `fetch_execution_failure_reasons` (`url`, `ids`: the surviving execution ids, one call) — the error summary, output/logs, and artifacts per execution.
4. Classify each (gate below), then show a **triage summary** — healable (case, one-line error), needs live check (case, the suspect step — wrong-element resolution is only decidable in the browser), and skipped (case, failure class, one-line reason) — and **ask for confirmation before opening the browser**.

**B. User names a case.** Resolve name → `id` via `fetch_test_cases` with that name as `name` (an ambiguous match is confirmed with the user, as in the update run). `fetch_test_case_last_execution` (`url`, `testCaseId`) — the case's most recent execution with its evidence. When it ran on a branch preview, use instead the newest execution on the deployed app from `fetch_test_case_executions` (`url`, `testCaseId`). If the execution used did not fail or time out, or there is none: tell the user there is nothing to heal on the deployed app, and stop. Otherwise classify from its failure evidence — status, error summary, output/logs, artifacts; when the response lacks the error detail, `fetch_execution_failure_reasons` (`url`, `ids`: that execution's id) fills it. No triage summary for a single case.

## Classification gate

Heal proceeds ONLY when the failure is a **locator failure**: element not found; a timeout waiting for an element to appear or become actionable; ambiguity (the locator matches more than one node — strict-mode violation); or **wrong-element resolution** — the locator resolves, but to a node that is not the element the step means, so the step acts on or reads the wrong element. The first three show in the failure evidence; wrong-element resolution rarely names itself there — it surfaces as a red assertion or a failure downstream of the drifted step, so at triage such a case is classed **needs live check**, not skipped, and its classification completes at the replay. The discriminator, live: resolve the suspect step's stored locator on the live page and compare the node it returns against the element's `name`, the old locator's role and accessible name, and the step's action kind. The intended node → the red is not a locator failure: out of scope, report. A different node → heal it: re-point the locator at the intended element (steps 4–6 below) and the original step and assertion must then hold **unchanged** — a check still red against the correctly-located element is a finding to report, never something to soften (the invariants stand). Map every error string through the failure table and honor its causes: the detached-from-DOM / submit-stays-disabled signature is a missing readiness pair, and a navigation timeout off an edited surface is a missing save/discard — both step-shape defects a heal MUST NOT touch (no added waits, no added steps): route them to a fix round. Everything else is out of scope and is REPORTED, never touched: assertion mismatch (except when the live check above shows the target's locator drifted onto a different node), navigation or network errors, auth or permission errors, server errors, data errors (duplicate records; the failure table's data-dependence row), and a whole-execution timeout with no step-level locator error. A "timed out" execution is undecidable until its detail is read — it can be either kind.

**Locating the failing step.** When the evidence names the failing step, use it. When it does not, match the error's locator against the case's steps' elements (`get_test_case` + `get_element`, below); still ambiguous → replay until the first failure.

## Heal procedure, per case

1. **Read the case:** `get_test_case` (`url`, `id`) — the stored steps, each referencing its elements by element id, the case's users, and `runViewport` and `runDevice`, the device its runs use; `get_element` (`url`, `id`) for the failing element's `name`, `locator`, `page`. Sign the case's users in (`references/platform-tool-modes.md`, _A case's users_) and make each of their browsers that device (`references/devices-and-browsers.md`, _An existing case_), since the app picks its layout from the size and user agent once per page load: every replay below runs each step in its own user's browser, as the device the failing run was. A locator measured on another layout can pass the replay and fail the next run. An `update_element` heal writes back on any device. A write that recompiles the script (an inline `selector`, step 8) follows _An existing case_ on a tablet or phone case: when `app_testing` takes no `device`, report the fix you found and leave the case unchanged.
2. **Replay live up to the step before the failure**, under the case's network rules (`references/platform-tool-modes.md`, _A case's network rules_). Every standing rule binds exactly as in authoring: the readiness pair after every navigation, one-shot refs re-acquired before every action, scoped reads of only the changed region, save/discard through the app's own control before leaving an edited surface (`references/local-adaptations.md`).
3. **State check:** the failing step's user's browser must be on the page the failing element is stored against (the element's `page`). Anywhere else → the fault is upstream of the failing step, not this locator: report and stop for this case.
4. **Find the replacement:** a scoped read of the step's surface in the failing step's user's browser. Identify the element by the old locator's role and accessible name, the step's action kind, and the element's `name` — the description of what the element is for.
5. **Exactly-one rule (HARD):** proceed only with exactly one plausible candidate — same role family, same container, neighbouring elements consistent. Zero candidates → the element was removed: report. Two or more → ask the user. NEVER pick the closest-looking element.
6. **Patch:** re-author `{ "pageUrl", "locator", "name" }` for that one element per the locator rules and the dialect ladder — the composed chain measured live to exactly one match, mappable vocabulary only. A locator that leads with `.frameLocator()` keeps those frame links: an iframe on the page is measured with them, and an extension panel's element is measured in the panel's app at its own URL and given the same frame prefix back (`local-rules.md`, _Extension side panel_).
   - **A step in an extension's side panel** (it carries `surface`) cannot be replayed here: a walk browser cannot open an extension. A case whose failing step, or any step the full replay below needs, acts in the panel is reported for an update run instead of healed.
7. **Validate — the whole case, live:** no platform gate runs on an existing case, so the green gate here is a full replay: every step of the case performed in order, every assertion's check confirmed true at its step.
   - Fails later on ANOTHER locator failure → repeat from step 2 for that step, for as many steps as fail on a locator.
   - Fails on anything non-locator → stop, write NOTHING for this case, report.
8. **Write back — all-or-nothing per case:** only when the full replay is green AND the user has approved the proposed locator diff (old → new, per element). Neither update tool takes a version, so the drift guard is procedural: re-read the element (`get_element`) immediately before writing — a `locator` different from the one classification read means someone else changed it: stop and re-classify. An element-referenced step → one `update_element` (`url`, `id`, `set`: the new `locator`, plus `name` when it changed) — every step and case referencing that element id heals at once, so the new locator must target the same intended node, never a different one that happens to pass. A step carrying a sanctioned inline `selector` instead → `update_test_case` (`url`, `id`, `set` on `properties.steps`, plus `properties.script` recompiled per the element write pipeline's step 6) with the array byte-identical except that one step's `selector` `value`/`name`. Verify by `get_element`/`get_test_case` re-read (`references/platform-tools.md`) before reporting success.

## Batch

Several cases failing on the same page + old locator usually share the element id — one approved `update_element` heals them all; still replay each of the other cases green (step 7) before reporting it healed, and a non-locator red among them is reported for that case individually. Distinct element ids carrying the same stale locator on the same page: heal the first, then propose the same old → new mapping as the patch for the rest — each still classified, replayed, approved, and written per this file.

## Diagnose — the root cause of a red that is not a locator

The heal loop (`app-test-heal-loop`) sends every red that is not a locator red, and every heal whose live check found the intended node, into a diagnosis: the same replay, read for a different question. Steps 1 to 3 above run unchanged — the case's users signed in, the `runViewport`, the readiness pair, every standing rule — up to the failing step; then the helper reads the page against the step and the description and names ONE root cause from the vocabulary (`app-test-triage-loop/references/taxonomy.md`, _Root causes_), with a finding a person can act on without opening the case and, where there is one, the fix. The rules that decide between the causes are the policy's (`app-test-heal-loop/references/policy.md`, _A diagnosis and its root cause_). Three habits keep a diagnosis honest:

- **Replay the whole case when the failing step passes live.** A step that goes green on the replay says nothing until every later step has too; the red may be two steps on. A case that replays green end to end with every stored step is `transient` — unless a step waited on a model's reply, which makes it `ai dependency`.
- **Read the app's own words.** A toast, an inline error, a reply that says a connection or a limit refused the request is the finding, quoted; a service's refusal is `backend` or `environment`, never the case's fault.
- **The two-strike rule binds.** The same action twice with the same result is final: `app bug` or `contradicts description`, never a third try.

A red whose `checksPassedBefore` is true (the entry says so) failed after every check of the case had passed: the diagnosis says what the cleanup hit, and keeps the flag.

## Update — re-author from the description

The heal loop's update job is the interactive update run (`platform-tool-modes.md`, _Update run_ and _Auto-heal run_) with the policy's clauses in place of the go-ahead (`policy.md`, _Before a re-delivery_). The saved description is the intent; the diagnosis (`rootCause`, `finding`, `fix`) says what has to change; the stored steps are context, never a memory source. The helper re-walks the whole case live as its users at its `runViewport`, authors the steps exactly as the rulebook, the adaptations, the dialect and `durability.md` say — self-provisioning, the readiness pair, the wait on a model's completion marker, every stated check with its subject and polarity — and builds the submission as `submission-contract.md` says with one difference: it carries the case's own `testCaseId`, `name`, `module`, `feature`, `scenario`, `description` and `userIds`, so the platform re-delivers the case in place and the green gate proves the new steps before they replace the old. Three deliveries at most, each after a fix the gate's output names. A stated check the app no longer satisfies twice is a `needs_answer`, never a softened assert; a surface that is gone, or an element only a position reaches, likewise.

## Report

End every heal run with (and record per-case outcomes in the run folder's `scenarios.md` when one exists):

- **Healed:** case, step index + element id, old locator → new locator (old is the stored locator the write replaced, as `get_element` read it, never one the case held before it broke), one-line reason. Mark **lower confidence** (`confidence: "lower"`; otherwise `normal`) when no later assertion depends on the healed step.
- **Skipped:** case, failure class, one-line reason — not a locator failure / upstream fault / no candidate / ambiguous / non-locator failure after patch / a case user who is no longer a test user.
- **Needs user input:** anything awaiting a choice.
