# Platform tools — the app-testing MCP

The platform's test-authoring tools are the `app-testing` MCP server, bridged to the signed-in tenant exactly like the builders' `application-builder`, `object`, `automation-code`, `agent-builder` and `code-builder` servers. Read this file before the session's FIRST app-testing call; every mode that names a tool below calls it this way.

## Calling a tool

- **Tools are `mcp__plugin_ua_app-testing__<tool>`.** Before the first call, load every tool the mode needs with ONE ToolSearch (`select:` with the exact names). Pass arguments only: the bridge supplies the tenant (the `host` that `login.mjs --check` printed), the cookie, the headers and the deadline.
- **The bridge is the only path to the tenant.** NEVER call `https://<platform-host>/…` yourself — no `curl`, no script, no `fetch` outside the app under test. A call made around the bridge carries no session and no person.
- **Result:** one text content item holding JSON — parse it. `isError: true` means the text is an error message, not data.
- **Deadline:** 60 seconds per call; `deliver_steps` gets 450, because its green-gate run alone takes up to 300. Nothing to set.
- **Availability**, read once per session from the tool list the ToolSearch returns:

| What you see | It means | Do this |
|---|---|---|
| a tool below is missing from the list | the tenant's deployment predates this file | say so; skip the mode that needs it |
| the server lists no tools, or a call is refused with `NOT_STARTED` | no UnifyApps Headless session in this folder | load the `setup` skill yourself, then try again |
| a call is refused with `AUTH_EXPIRED` | the session lapsed | sign in again by loading the `setup` skill yourself; retry once |
| every call fails with an HTTP error from the bridge | the tenant does not serve app-testing | tell the person; skip every mode that needs these tools — authoring needs none, submission needs `deliver_steps` ([submission-contract.md](submission-contract.md)) |

- The `url` argument every tool takes is the **platform screen URL** (`https://<tenant>/p/0/interfaces/<interfaceId>/…`) — never the matrix/deployed URL. The tool reads the host and interface id from it. **Exception:** the tools below that also take `interfaceId?` (`list_test_users` and the suite/plan/run tools) accept a matrix (deployed app) URL plus an explicit `interfaceId` — `interfaceId`, when given, is used before the URL's path is ever inspected, so only the URL's host still matters. Always pass `interfaceId` explicitly with a matrix URL on these tools: a matrix URL has no `/interfaces/<id>/` segment, the same as a genuine platform screen with no app open, so an omitted `interfaceId` on a matrix URL does not error — it silently resolves the call as platform-scoped instead of to that app, because the resolver has no way to tell "a real app's deployed URL" apart from "no app open."

## Resolving the platform screen URL from a deployed app

When the run started from a deployed URL (`https://<app-host>/…`) and no platform screen URL was given, resolve it yourself — never ask the user for it, and never guess:

1. `GET https://<app-origin>/auth/domain-mapping/platform` — unauthenticated, read-only. Returns `[{"customerId": …, "domain": "<platform-host>"}]`; take `domain` from the first entry.
2. `GET https://<app-origin>/auth/interface/deployed` — the same sanctioned read the submission contract uses for `interfaceId`; its `id` is the interface id.
3. The platform screen URL is `https://<platform-host>/p/0/interfaces/<interfaceId>/tests/test-cases`. Record it in the run header of the run's ledger (`scenarios.md`, or `results.md` for scenarios from another source).

If either GET fails or returns no usable value, ask the user once for the app's platform screen URL. The reverse direction — platform screen URL → deployed URL — is ONLY `derive_matrix_url` below: never read the deployed URL off the app's overview or app-details page in the platform UI, and never assemble it from domain conventions.

## The session cookie

Every call rides the **UnifyApps Headless plugin's own platform session** — the `_at` cookie its sign-in saved. The bridge reads it from the OS secret store (macOS Keychain, Windows DPAPI, Linux Secret Service; a private file on a machine without one), fresh for each call, and sends it in-process to that tenant alone. You never receive it: it is never in a command you type, your output or a file you write.

Hard rules:
- NEVER ask the person to sign in to the platform for these calls, and NEVER read the cookie from the browser. The login wall in the authoring flow is the app under test's own sign-in, a separate thing that stays as it is.
- `AUTH_EXPIRED` has one fix: sign in again by loading the `setup` skill yourself, then retry once. NEVER fall back to a browser sign-in or ask for a pasted cookie.
- Response bodies go to `scenarios.md`, a report, or an authored step as data — nowhere else.

All of `list_test_users`, `create_test_suite`, `update_test_suite`, `delete_test_suites`, `fetch_test_suites`, `get_test_suite`, `create_test_plan`, `update_test_plan`, `delete_test_plans`, `fetch_test_plans`, `get_test_plan`, `run_test_suite`, `get_test_suite_execution`, `run_test_plan` and `get_test_plan_execution` take `interfaceId` as an explicit override of what `url` would otherwise resolve to — omit it and let the URL decide (the normal case, and the only one these run in); pass it only when the subject is the platform's own Test Studio screens (no app open) rather than one specific app, or the subject otherwise differs from the URL you have.

`fetch_test_suites`/`get_test_suite`/`fetch_test_plans`/`get_test_plan` are real reads for the suite or plan **record** itself, the same `fetch_test_cases`/`get_test_case` pattern one level up — resolve a suite or plan id from its own `create_*` response, from the user, or from a fetch-and-scan-by-name (`suites-and-plans.md`, _Resolving a suite or plan id_); no server-side name search on either list tool. `get_test_suite_execution`/`get_test_plan_execution` stay real reads too, but for an **execution** record, never the suite/plan record — that distinction still matters.

Reads (`derive_matrix_url`, `get_app_run_viewport`, `list_test_users`, `fetch_test_cases`, `get_test_case`, `fetch_failed_executions`, `fetch_execution_failure_reasons`, `fetch_test_case_last_execution`, `fetch_run_executions`, `fetch_test_case_executions`, `get_artifact_content`, `get_element`, `search_elements`, `fetch_test_suites`, `get_test_suite`, `fetch_test_plans`, `get_test_plan`, `get_test_suite_execution`, `get_test_plan_execution`) and the four pure transforms (`parse_curl`, `extract_elements`, `generate_element_candidates`, `replace_elements_with_ids`) are yours to make whenever a mode needs them. Writes (`create_or_update_test_user`, `update_test_case`, `delete_test_cases`, `create_element`/`create_elements`, `update_element`, `delete_elements`, `create_test_suite`, `update_test_suite`, `delete_test_suites`, `create_test_plan`, `update_test_plan`, `delete_test_plans`) fire only on the user's explicit request or per-item confirmation — never as a side effect — with two bounded allowances: the sign-in flow's automatic `create_or_update_test_user` when the app has no test user at all (SKILL.md, _Sign in as a test user_), and element creates/updates that persist the elements of a step write-back the user already approved — part of that one approved write, never free-standing. `deliver_steps` is the submission itself and follows the authoring run's one-time go-ahead (SKILL.md, _Authoring run_), never a per-case prompt. `run_test_suite`/`run_test_plan` need no separate go-ahead beyond whatever already covers the suite or plan's own existence — like `run_test_cases`, they never mutate a record, only run one that was already approved.

**Which fields are safe to `set`:** only ever set fields you have observed on the case via `get_test_case` (or on the element via `get_element`) — `name`, `tags`, a `properties` sub-field by its own path (`"properties.<field>"`), an element's `locator`/`candidates`. Never `properties.users` or `properties.user`: who a case runs as is the maker's choice in Test Studio, and no local run changes it. There is no `testSuites` field on a test case — suite membership lives the other way round, on the suite's own `testCaseIds`; to group a case into a suite, use `create_test_suite`/`update_test_suite` instead (`suites-and-plans.md`). **Never `set` `properties` as a whole:** it carries a hidden type label (`_t`) that no read shows and a whole-bundle write drops, so the case reads back with empty `properties` — no steps, no script. After any `update_test_case` or `update_element`, re-read with the matching get tool and confirm the stored value is the one you sent before reporting success.

## Running on another domain

`run_test_cases`, `run_test_suite` and `run_test_plan` take an optional `domain`: the host the run opens instead of the app's own, such as a pull request's preview. Only the host changes; each case keeps the path it was recorded on. It applies to that one run; nothing is saved to the case.

- **Where it comes from.** A host or link the person gave, a preview link a skill reads from the pull request itself (`app-test-affected`), or the `DOMAIN` of the run you repeat when a loop says so. NEVER build one from a PR number or a branch name. Asked to run on a preview with no link: ask for the link, and NEVER run on the default domain in its place unless the person chooses that. Omit `domain` for a normal run.
- **What is refused.** A link works: only its host is sent. A host or link with a port, or text that is not a host, is refused before anything runs. Show the error and ask for the host without a port; NEVER run again without `domain` in its place.
- **Where the cases really ran.** The reply does not say: the platform runs a host it does not allow on the default domain and still answers with the usual run map. Read the `DOMAIN` of each finished execution with `fetch_run_executions` (`runId`: an execution id the run answered, then its `TEST_SUITE_RUN_ID` or `TEST_PLAN_RUN_ID`; `failedOnly` false, so the passes are read too), or `fetch_test_case_last_execution` per case. A host other than the one you sent means that case ran there instead: say so, and NEVER report it as a run on the preview. No `DOMAIN` at all means the tenant does not record it yet: say the host is not confirmed.
- **A branch preview** is a `DOMAIN` that ends in `.vercel.app`. Its reds belong to the pull request: the heal loop and the ticket loop set them aside, except a red the run service or an environment event (the preview's sign-in, the runner, the tenant) stopped, which keeps that standing.

## Reading and writing a case — MCP only, never the Test Studio UI

`fetch_test_cases` is the list projection (existence, `id`, `name`, `description`, last run status, `hasScript`); **`get_test_case` is the definition** — the stored steps, each referencing its elements by element id, which `get_element` turns back into locators. Every read of an existing case or element goes through these tools, and every change goes through the write tools above. **Never open a case in Test Studio's UI to read or edit it: no clicking into the step editor, no retyping an expected value, no saving in the browser.** The browser's job in every mode is walking the **app under test**; the auto-heal run's locator validation happens there — on the live app's DOM — not in Test Studio. In an auto-heal run the intent source is the case's saved `description` from the fetch; the steps `get_test_case` returns are what you validate against it (SKILL.md, _Auto-heal run_). A case without a `description` keeps the old behavior: its steps/script are the intent source.

## The element write pipeline — inline locators → persisted ids

A **submission** (`deliver_steps`, SKILL.md, submission contract) takes steps with inline `{ "pageUrl", "locator", "name" }` elements and persists them platform-side — nothing to do there. A **steps write-back** through `update_test_case` does not: the stored steps reference elements by id, so freshly authored steps must have their inline elements persisted and swapped for ids first. The order, all before the one `update_test_case` call of the approved write:

1. `generate_element_candidates` on the authored steps — derives each element's `candidates` from its locator; any error means the locator shape isn't storable: re-derive the locator, never force it through.
2. `extract_elements` — the flat list of inline elements the steps carry.
3. `search_elements` (scoped by `pageId` where known) — reuse a persisted element that already matches instead of creating a duplicate.
4. `create_elements` for the rest — the walk's genuinely new elements.
5. `replace_elements_with_ids` with the persisted list — the steps come back id-referenced; an `unmatched` entry is a missing create, not a license to invent an id.
6. `update_test_case` `set` with `properties.steps` (those id-referenced steps) and `properties.script` (those steps compiled with the `app_testing` tool — the runner executes the script, not the steps — with the case's `runViewport` as `viewport` and its `runDevice` as `device`, verbatim: [devices-and-browsers.md](devices-and-browsers.md), _An existing case_), then the `get_test_case` re-read that verifies both. Compile for the case's own users: `users` is the case's users as `get_test_case` reads them, in that order, each as `{ "id", "name" }` with the name from `list_test_users` (the platform's listing for a case of the platform), and a private app also sets `injectAuthCookie: true`, which signs each user in; a public app sends neither. When `properties.networkRules` holds any rule, call `app_testing` with `networkRules` set to that list, unchanged and in order: the script carries the rules, so a compile without them saves a script that no longer applies them while Test Studio still shows them. A compile that answers a `network rule "` line, or refuses `networkRules` as not fitting its input, means a saved rule is incomplete or no longer fits the rule shape: stop and tell the person which rule. Never set `properties.networkRules` yourself, or drop or turn off a rule the maker saved: a change that needs a new or different rule is reported, for the maker to make in the case's Network tab in Test Studio.
