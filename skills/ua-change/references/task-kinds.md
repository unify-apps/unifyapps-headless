A `publish` of an AI agent (entity kind `ai-agent`) goes to agent-builder.

`page-layout`, `page-bind` and `publish` build a no-code app, one the application builder edits page by page. `code-app` and `code-publish` build a code app: a React app whose source Code Builder's engine keeps in git, which the code app agent changes from a local checkout (`app-code-build`). Its Touches line and its task's entity use the kind `code-app` (`- code-app · <name> · <app id or new>`), and `## Ready when` authorises its publish as `publish <name>`. The first `code-app` task of a new app creates it. One `code-app` task is one change to one app, committed as one push: the code, its dependencies, and the app's CSP when the change needs it.

Code app work goes one app at a time, because an app's tasks share its checkout and its branch. A code-app-agent batch holds the ready tasks of one app, and nothing else of that app starts while one of its tasks runs. One agent keeps one app: a later change, a retry or the publish goes back to the agent that last worked on that app, which already holds the checkout, when it is idle and no task was handed back twice; otherwise `plan ready` starts a new agent.

## Dependency rules

The exact edges a plan writes ([order-of-work.md](order-of-work.md) gives the order). `plan propose` refuses a plan that breaks a rule the code checks, and names the fix.

1. Add a dependency only when a task uses the other task's id or output. Every extra edge makes work wait.
2. A new app has one `app` task, on entity `{kind: "app", name, id}`. It creates the app and stores its look. A new global module has one too, on entity `{kind: "app", name, module: true}` with no id: the platform makes a module's id, so no task of it names one, and its pages take the id from `Built so far`. An `app` task on an existing app stores a look change. Every `page-layout` of that app in the plan depends on it. Layouts of one app do not wait on each other.
3. The new app's id is fixed once in the plan: lowercase letters, digits and single hyphens (`field-ops`). It becomes the app's sub-domain. Each page carries it in `entity.appId` and names the app in `entity.app`. The `app` task and the publish carry it in `entity.id`. It is free when `get_app_overview` answers not found.
4. A `page-layout` never depends on a backend task (object, record, automation, shell, deploy, ai-agent, evaluation, api, env-variable, connector).
5. A page with a `job` line gets a `page-review` on that page. It depends on the page's bind, which depends on the layout, so the review judges the page with real data; with no bind in the plan it depends on the layout. The bind never waits on its own page's review. Every other task that depends on that layout (the bind of a page that links to it) and the app's publish depend on the review.
6. A `page-bind` depends on its layout (or its review), on every object it uses, on the shell of each new automation it calls, and on the layout of every new page its actions open. A bind on an existing page may depend on nothing.
7. A bind that waits on a shell sees only stub values. Its proof checks the bindings and the call. A proof that needs real data goes on the publish, or on a task that waits on the real deploy.
8. An existing automation is never shelled. A bind on it depends on nothing when its contract stays the same, and on its `deploy` when the contract changes.
9. A `deploy` depends only on its automation task. A `publish` depends on the binds of its app and on the deploy of every shelled automation they use, so nothing goes live over a stub.
10. A task that runs an automation (a test run, a suite, a proof that runs it) depends on the `deploy` of every new or changed automation it calls. A caller reaches the deployed copy, never the draft.
11. An object task depends on the task that creates each object its lookups point at. Two new objects that point at each other: create the first without that lookup, then add it in a third task after the second.
12. A menu entry for a new page goes in that page's own layout or in the app's publish. `apply_navigation_edits` refuses an entry for a page the app does not have yet.
13. An `ai-agent` task depends on every automation it binds as a tool, through its shell when one exists. An AI agent's `publish` depends on its `ai-agent` task, and `## Ready when` names `publish <agent name>`. An `ai-agent` task never publishes, except a graph's discoverer or cleaner (rule 22). Publishing alone does not put an agent anywhere: an agent meant to sit in a Copilot block needs `deploy_agent` too (`agent-builder` § Where it runs), in the `publish` task itself or a task that depends on it, never folded into the `ai-agent` task. An `ai-agent` task on a knowledge set (entity kind `knowledge-set`) comes before the `ai-agent` task of every agent the set is given to. A knowledge set is never linked to the solution: its row and link in the entity table are how the person finds it.
14. An `experiment` depends on the dataset and metric tasks it names and on the `ai-agent` task of the agent it grades. A derived metric depends on its base metrics. A dataset and a plain metric depend on nothing.
15. A run of an experiment costs real model money for every test case. A task starts one only when its body says so, and its builder asks the person first.
16. A task that deletes says what in `deletes`, in plain words (`"the 3 TEST rows of Request"`). The person is asked before it is sent, in every plan. A cleanup of rows a task did not create is its own task with `deletes`.
17. An `api` task on an API depends on the `deploy` of the automation it runs when this plan deploys it: an API answers an error until its automation is deployed. That automation's start trigger is `callables_from_api` (a Callable API) or `webhooks_default` (a Webhook API), and `save_api` refuses any other. An automation a page or an AI agent calls starts with `callables_from_automation`, so it cannot back an API: the plan adds a small API automation that calls it, with its own `automation` and `deploy` tasks, and the `api` task runs that one. A GET API has no request body, so its automation's `Callable from API` inputs must be ones the call sends as query parameters (`?name=value`); an input only a POST body can carry answers `<FIELD>_REQUIRED` on every GET call, however the trigger is set. An access profile task depends on the tasks of its client and of every API Group it lists, and a task that attaches a policy depends on the tasks that make the policy and what it attaches to. Making an API live is not a release and has no `plan confirm`. A key rotation (`rotate_access_profile_key`) is asked about like a delete: `deletes` names the old key. An API Platform record is never linked to the solution (only apps, code apps, objects, automations, AI agents and connections are): its row and link in the entity table are how the person finds it, so no `## Ready when` line, proof or summary says it is linked.
18. A task that runs, tests or publishes something that reads an environment variable a task of this plan creates depends on that `env-variable` task, and so does the `page-bind` of a page that reads it: a missing variable reads as empty and the run can still look green. Saving an automation does not check the name, so a plain `automation` task need not wait. An `env-variable` task never carries a secret: a secret is saved by the main session in chat ([SKILL.md](../SKILL.md) § Secret values), so a plan reads it as existing. The task creates only a setting that is not secret, with the value the spec states, or changes `sensitive`, shares or deletes. A secret the person has not given gets no task: the reader's task carries the `Security:` line instead (`ua-secure-by-default`). A delete is asked about like any other, and `deletes` names the variable. An environment variable is never linked to the solution, the same as an API Platform record.
19. A custom connector reaches automations only once it is published, so an `automation` task whose step uses a connector a task of this plan builds depends on that `connector` task, and that task ends with `publish_connector` when the spec says it ships. A connection to it is the person's to make: a run or test that needs one waits on a `manual` task. A `connector` task never carries a secret value: credentials are connection fields read through templates. A delete is asked about like any other, and `deletes` names the connector and the ids or types. A custom connector is never linked to the solution.
20. Two `code-app` tasks on one app chain, one depending on the other, because they share its checkout; `plan propose` refuses them otherwise. A `code-publish` depends on every `code-app` task of its app, and `plan propose` refuses it otherwise: the engine refuses a publish while the branch is held. A `code-app` task uses objects and automations like a `page-bind`: it depends on every object task whose records it reads or writes, on the `automation-shell` of each new automation it calls (rule 6), and on the `deploy` of an existing one whose contract changes (rule 8). A `code-publish` depends on the deploy of every shelled automation the app calls, so nothing goes live over a stub (rule 9).

21. A `governance` task on a role depends on the task of every app whose permission groups it grants, because a group cannot be granted before the app that defines it exists. A task that gives a role to a person or a team depends on the tasks that make the role and that principal. Giving a role is never a release and has no `plan confirm`. Three governance calls are asked about like a delete, so `deletes` names what goes: `delete_user`, `delete_team` and `delete_role`, and a password reset (`reset_user_password`), which destroys the password its holder signs in with. **Giving a role to a principal REPLACES every role it held in that scope**, so a task that means to add one names in `deletes` any role the change takes away, read before the write. A governance record is never linked to the solution, the way an API Platform record is not: no `## Ready when` line, proof or summary says it is linked.

22. A context graph is several `graph` tasks in the stages of `context-graph-sources/references/build-order.md`: first the graph, its publish, node and edge types, node settings and rules, the source and its object scope; second, the source's Discover & Enrich configuration, mappings, the source publish and the projection check after the first record of each node type; last, record edges and the search automation. A `graph` task depends on the stage before it and on the object or automation tasks whose output it loads records from; the second stage also depends on the `ai-agent` task of every discoverer or cleaner it binds, because that configuration names the processor's published version. Each task names the nodes and edges it builds in `graphNodes` and `graphEdges`, only from the spec's `### Context graph` part: `plan propose` refuses any other name, and a stage that builds none carries empty arrays. A discoverer or cleaner `ai-agent` task depends on the first stage and publishes the agent inside its own task: nobody uses it directly, so it needs no `## Ready when` line. The consumer's `ai-agent` task depends on the last stage, because `bind_graph_search` needs the search automation it builds, and its `publish` follows like any AI agent's (rule 13). A graph task's entity is the graph (`{kind: "graph", name, id?}`) in every stage. A graph is never linked to the solution: its row and link in the entity table are how the person finds it.

## Automation shells

A shell lets binds start before the logic is done. Split a new automation that a page, a code app or an AI agent calls into two tasks:

- `automation-shell` depends on the objects its schema names. `## Ready when` names `deploy <that automation>`.
- `automation` (the logic) depends on its shell and on the objects it writes. It opens the shell's `workflowId`, keeps the contract and does not deploy. The `deploy` task depends on the logic.

A shell body is these five lines, filled in:

1. Read: `search_workflows` for `<name>`. If it exists, stop and report: a shell is only for a new automation.
2. Create the callable automation with `setup` = `<exact input fields and types>` and `result` = `<exact output fields and types>`, and a stub body that returns a typed value for every output.
3. `compile_and_save_workflow` with no `workflowId`, fixing every finding until it saves.
4. `deploy_workflow` with that `workflowId`, deploymentNotes `Contract shell for <name>`. Step 3 must be the last save.
5. Read back `search_workflows` for its `deployment` and `describe_callable_workflow` for its inputs. Report the `workflowId` in `ids.entity`.

## What each builder can do

A builder calls only the tools on its own servers. `plan propose` refuses a body or proof that names another builder's tool (`scripts/lib/tool-servers.json` says which server holds each tool). It matches the tool's name anywhere in the text, a sentence that only explains why included: name another builder's work in words ("saving that automation"), never by its tool. That check catches a tool name, not a worded-around ask: never fold a check that belongs to another kind, such as an automation dry-run, into an `object` or `record` task's acceptance criteria — fde-agent has no automation-code tools to run it. Give that check its own `automation` or `automation-shell` task instead.

| Agent | Kinds | Servers |
|---|---|---|
| fde-agent | object, record, api, env-variable, connector, governance | `object`, `api-gateway`, `connectors-sdk`, and `list_connections` and `get_connection_schema` from `connection`. **The governance tools are not granted yet**, so a `governance` task is refused until they are: the kind routes here, the tools follow when a tenant serves them |
| automation-agent | automation, automation-shell, deploy | `automation-code`, `object` |
| app-agent | app, page-layout, page-bind, publish | `application-builder`, `object` |
| agent-builder | ai-agent, dataset, metric, experiment | `agent-builder`, `evaluation`, and the graph-role tools of `context-graph` its agent file names one by one |
| graph-agent | graph | `context-graph` |
| code-app-agent | code-app, code-publish | `code-builder` |
| page-reviewer | page-review | none: it judges shots and an outline |
| the person | manual | every tool, in the main session |

When this file does not settle which tool makes a change, load the tool's schema with ToolSearch, or read the sheet with `get_app_builder_knowledge`. A change no tool makes is a `manual` task, or leaves scope as a stated assumption. A proof never asks for a read no tool gives.

The read that proves each fact:

- **fde-agent.** Object fields, indexes and settings: `get_objects`. Stored rows: `get_records`. An API Group, API, client, access profile or policy: `get_api_group`, `get_api`, `get_client`, `get_access_profile`, `get_policy`. That an API answers: `call_api`. An environment variable: `get_env_variables` by exact name, its row under `found` with `sensitive` and `version`, or the name under `missing`; never quote its `value`. A custom connector: `get_connector`, and `get_connector_action`, `get_connector_trigger` or `get_connector_authentication` for a part in full; `published` says whether automations can use it. A user, team or role, where the tenant serves the governance tools: `get_user_details`, `get_team_details`, `get_role_details`; what a principal holds is read by the dry run of `apply_role_mapping_edits`, since nothing else reads it.
- **automation-agent.** Inputs: `describe_callable_workflow` (it lists only the parameters a callable accepts). Outputs: the `result` schema in `open_workflow`'s code, or the START node of a test run. Deploy: `search_workflows`. An automation's best practice score and the checks it fails: `get_workflow_best_practice_report`. A run: `trigger_workflow_run`, then `inspect_workflow_run`.
- **app-agent.** Blocks, bindings, data sources: `get_blocks`, `get_page_outlines`, `get_data_sources`. Page addresses: `get_page_paths`. A page's best practice score and the checks it fails: `get_best_practice_report`. Menu and default page: `get_navigation`. App variables: `appVariables` from `get_app_overview` (`get_context_keys` lists none). The app's name: the `update_app_settings` reply (`get_app_overview` does not show it). A publish: the `publish_app` reply or `list_interface_versions`. A page's own system bars: the `update_page_settings` step writes `statusBar` and `navigationBar` as `{style}` only, `light`, `dark` or `auto` (lowercase, no binding); `null` hands the bar back to the app theme's value, and an unset `navigationBar` copies the status bar. `apply_page_edits` never refuses on four guards, it only returns `warnings[]`: a scrolling Repeatable inside a same-axis scroller on MOBILE apps; a block-input `{{ }}` expression over `MAX_BINDING_EXPRESSION_CHARS` (200) characters, or one that holds a function or an array method; a block that clears its state when hidden, behind a visibility condition, while other blocks read it; and every `executeScript` it stores (also through `update_event_actions`). The page quality pass's P2 runs the same test on each `{{ }}` expression of `content` and `appearance` (a function, `.filter`, `.map`, `.flatMap`, `.reduce`, `.sort` or `.forEach`, or over 200 characters): blocking inside a template repeated per row (a Repeatable row, a mapped Carousel slide), advisory elsewhere. The same call stores mobile `additional.customCSS` pretty-printed. `update_blocks` writes `appearance.interactions` only on a Pressable and refuses it on every other block.
- **code-app-agent.** A code app's head, `gitLinked` and deployment: `get_code_app`. Its source: the checkout `get_branch_codebase` writes. Its name, privacy and CSP: `get_code_app_settings`. Its history: `list_code_app_versions`.
- **graph-agent.** A graph and its schema: `get_context_graph`, `list_context_graph_nodes`, `list_context_graph_edges`. A source, its objects and mappings: `get_context_graph_source`, `get_context_graph_source_objects`, `get_context_graph_source_mappings`. Records and their links: `run_context_graph_cypher_read` (a record read can list no edges for a link Cypher shows). A node's rules: `get_context_graph_node_survivorship`, `list_context_graph_node_match_rules`, `list_context_graph_node_data_quality_rules`. Parked matches: `list_context_graph_review_queue`.
- **agent-builder.** Settings, tools and skills: `get_agent`. Knowledge: `get_knowledge_sets`, `get_knowledge`, and that it finished indexing: `check_knowledge_status`. Answers: `send_test_messages`. Dataset: `get_dataset`, `list_dataset_items`. Metric: `get_metric_details`, and its score on a sample: `test_metric`. Experiment: `get_experiment_details`, and whether it can run: `check_experiment_readiness`. A run's result: `experiment_scorecard`, never a mean worked out by hand. Whether the tenant can do evaluation writes at all: `check_evaluation_automations`.

Work that is not a builder task:

- **A connection.** Builders only read connections. A new or changed one is a `manual` task: the main session makes it with `connection-manager`.
- **The solution's name or description.** The main session changes it with `update_solution {id, expectedVersion, name?, description?}` on the `solution` server when asked, `expectedVersion` being the solution's `version` from `get_solution`, and reads it back with `solution context`. Never change anything else through it. It is not a plan task.
- **Deleting the solution.** `delete_solution {id}` removes the solution record only: its specs, plans and documents and every object, automation and app it linked stay. It cannot be undone, so say what stays and ask first.
- **App settings with no page and no publish**, other than the look: a `manual` task.
- **A mobile app's icons and splash screen.** The main session makes them from the person's logo and sets them on the app with the `app-brand-assets` skill, in chat and in a plan alike. No builder agent does it.
- **A mobile app's push notifications.** The main session sets them up with the `native-push-notifications` skill (Firebase project number, service-account key, notification icon and colour), in chat and in a plan alike. No builder agent does it.
- **A mobile app's builds and releases.** The main session makes them with the `native-release` skill (test APK, AAB, iOS build, store release, over-the-air update), in chat and in a plan alike. No builder agent does it.

Work no tool does:

- **A tab bar's colours or labels.** Theme colours are different: an `app` task writes them with `set_app_theme`, or in the app header where the tenant has no theme tools. `update_app_settings` only picks which theme the app uses.
- **Menu items** have no condition and no count badge. They can be limited to existing permission groups. Groups hold one level, and mobile apps draw no groups.
- **The menu's look**: where it sits, its kind (side, top, bottom tabs, drawer, none), its styles, page transitions, a home page chosen by a condition. One exception: WHAT draws the bar — the platform's own bar or a module of the app — is an `app` task written with `set_navigation_style`, where the tenant serves it. The full list is in `app-design/references/navigation.md` § What no tool can do yet.
- **The global page.** Its blocks never render. A header on every page is built on each page.
- **Code apps.** An app whose `cache app` says `mode code` is a code app: the app-agent never writes its pages or data sources. A `code-app` body names the files or screens it changes and what each does, never a patch or file contents: the builder writes the code. Its proof is the push's `commit` and `files`, and `get_code_app` answering that commit as its `head.sha`; a `[visual]` proof looks at the change in the local dev server or the preview. A `code-publish` body is `publish_code_app` with the `versionNote` it requires, which the engine refuses while the branch is held; its proof is the reply's `deployed` read-back, deployed with the `commitHash` of the last commit the plan pushed, or `get_code_app`'s `deployment`. The publish adds a `publish v<n>` commit of its own, so the head moves past the deployed commit; a proof never compares the two. An app that `get_code_app` answers `gitLinked: false` is worked on `main` only, so a body names a branch only for a git-linked app. A body never tells the builder to install software or to run a script from the app. A `code-app` task names the objects whose records it reads or writes, and each automation it calls with the input fields the app sets. Its builder makes the data sources with `create_code_app_data_sources`, as a page-bind makes a page's: the app's Storage set once per app, and one per automation. The task's proof includes a non-empty `FETCH` id in the committed `app/src/data/bindings.ts` when it reads records, and each automation's block in the committed `app/src/data/callables.ts`. A code app's name, privacy or CSP is a `code-app` task too, written with `update_code_app_settings` (never `set_app_visibility` or `update_app_settings`, which refuse a code app); its proof is that tool's read-back. A `code-app` task that brings back an earlier version names it, as a published version number or a commit from `list_code_app_versions`, and says what restoring it undoes; its proof is the restore's `commit`, `get_code_app` answering it as `head.sha`, and `compare_code_versions` against that version answering `same: true` or naming only the files the restore `kept`. A restore publishes nothing: going live is a `code-publish` task after it.
- **Table search.** The toolbar search fires no event. On a table that reads an object it narrows the fetch. Any other source is not narrowed.
- **Hand grading of a run** (human in the loop). The person does it in the Evaluation screens.
- **Copying a dataset.** Read the old test cases with `list_dataset_items` and add them with `add_test_cases`, or import.
- **AI agent temperature.** An agent has only the settings `create_agent` and `update_agent` take.
- **Agent tests with context.** `send_test_messages` sends plain messages. Put any context the agent reads into the message itself.
- **The browser console.** No tool reads it, so a proof never counts console errors.

## Facts every body follows

- **Best practice score.** The app-agent reads a finished page's score and the automation-agent reads each saved automation's, and each fixes failing checks toward 90 on its own, so a body need not ask for it. A contract shell is not scored. The report states the score, and each exception it left is a `notes` line that starts `best practice exception:`; the person is told both. A brief never tells a builder to skip test runs after it changes code to fix best-practice checks: the builder still runs the task's tests on the version it ships.
- **Deploy proof.** `search_workflows` returns `deployment` (`status`, `deployedVersion`, `definitionVersion`, `deployedAt`). `open_workflow` returns code and the saved version only. `definitionVersion` is the saved version that went live, so a proof compares it with the version the logic task saved. `deployedVersion` only counts deploys (1 on a first deploy, whatever the saved version), so a proof never sets it equal to a saved version.
- **Publish proof.** The `publish_app` reply (`liveUrl`, and `pageUrls` with the default page at the root), or `list_interface_versions {kind: "published"}`. `get_app_overview` has no deploy state. A publish does not re-check its deploys: the app-agent cannot call `search_workflows`. A reply of `alreadyLive: true` (`published: false`) means another publish, perhaps another plan's, already shipped this draft: no version is made and the `deploymentNotes` are dropped. So a publish proof never needs a version past the one step 1 read, or this plan's notes on it; it reads the task's change on the live version.
- **Visual proof of a published page.** Open the tenant's preview route, `…/preview/<path>`. Never `liveUrl` or a `pageUrls` address: they are on another host with the app users' sign-in.
- **Page job, design and app look.** A new page has a `job · <page>:` line and a `design · <page>:` block in `## Contract`. A new no-code app has an `app look · <app>:` line above every job line. Pages that pass values between them have one `state · <app>:` line, which every layout and bind of that app gets. `app-page-planner` writes them. A layout body does not copy them: `plan propose` hands them to the page's tasks. The body says what must be true when the page is done, never which block goes where.
- **A record-change trigger needs the object to allow it.** A trigger on `storage_by_unifyapps_on_any_change` is refused at compile until the watched object has `logging.supportsWebhook` true, which is off by default. A plan with such a trigger on a new object sets it in that object's own task (`update_object_settings`), and the automation task waits on that task.
- **Analytics SQL needs reporting on.** An Analytics query sees an object's rows only while its `logging.captureReporting` is on, and turning it on copies no row already stored: only rows saved after it reach Analytics. So the object task turns it on before any row is written, or a later task saves the old rows again with the same values.
- **Copying a page.** Use `copy_pages`: the copy lands in its source's folder with new ids, and `update_pages` gives it another address. A bind on the copy reads the copy's ids first. `copy_entities` copies blocks, variables, functions and data sources within one page only and refuses another page: a part another page needs is built again there from the read config.
- **Sign-in pages.** Every app already has working login, signup, mfa-verification, forgot-password, update-password and reset-password pages: the platform serves its own until the app holds a copy of its template, so no plan builds them and no page gets a job line for one. A page put at `/login` by hand is an ordinary page the app never shows, so the bridge refuses `create_pages`, `update_pages` and `copy_pages` at those top-level addresses. Only when the person asks for their own look or words on one does the app's `app` task copy the platform's template, with `create_auth_pages` where the tenant serves it. Send one kind per call: when a kind has several templates the call is refused with their ids and names, and it names only the first such kind, so a call with two kinds takes three tries. Send it again with `templateId`, and keep every sign-in page of one app on one family of templates (all named "Platform …", or none), so the pages look alike. A kind the app already has answers `existing` with its page id: edit that page. The copy keeps its address and the id the sign-in service serves: `<appId>_login`, `<appId>_signup`, `<appId>_mfa_verification`, `<appId>_ua_governance_forgot_password` or `<appId>_update_password`. It is then edited like any existing page; it keeps the template's logo until a task changes it. Where the tenant does not serve the tool, adding the page is a `manual` task: App Builder → Add page → Templates. A published app shows the copy only after its next publish. Reset-password has no template and stays the platform's.
- **Event actions.** Adding or removing a follow-up action of a stored action resends that whole handler, which gets new `evt_` and `act_` ids. So a proof names an event by its block, its event and its actions, never by an `evt_` or `act_` id read before the write.
- **Page variables.** A page variable is made in the page's own `apply_page_edits` (`create_page_variables`). `update_page_contracts` sets only a page's inputs, outputs and custom events, never its variables.
- **A shared module shows what it is given.** A module (a page placed on other pages with the `module` block) that has no data source of its own gets its values from the page inputs each page fills in. So every page that places a module showing data has a bind that fills those inputs, or the module gets its own data source.
- **No version numbers.** Every save moves the version. Write "higher than the version step 1 read".
- **Page addresses.** An address ends in a plain word (`/home`, `/cases/:caseId/detail`). `create_pages` refuses `/` and a last `:param`. A page opened from a link that carries a token (an invite or sign-in link) keeps the token before a plain last word, such as `/t/:token/enter`, and the automation that builds that link uses the same address. A home page gets a plain address, and its layout makes it the default page with `apply_navigation_edits` op `setDefaultPage`. Its proof reads `defaultPageId` from `get_navigation`. Moving a page to another address is `update_pages` (`slug` or `path`): `update_page_paths` only shapes the path folders.
- **Stored values.** A picklist stores the option's code (`in_progress`), never the label. A date stores epoch milliseconds. The object task names each code with its label, and every page task that shows, filters or writes the field uses the same codes.
- **Update by id is not an upsert.** `storage_by_unifyapps_update_record_by_id`, in a page data source or an automation, writes nothing for a record id that does not exist yet (`success: false`) unless `upsert` is `true`, which is `false` by default. A task that creates or updates one record by a known id names `upsert: true` in its body.
- **Field names in object steps.** `apply_object_batch` fields, `required` and index `fields`, `apply_record_edits` properties and `get_records` filters take the plain name (`pm`), never the column (`properties_pm`) that cached reads and data sources show.
- **Object field properties.** Types, keys and index ops are in `object-storage-manager` § Object schema format. Point the body there.
- **Record ids.** The platform sets a record's id and refuses a write that sends `id`. A `primaryKey` field's value becomes the id. A task that needs a known id sets a `primaryKey` field. A `primaryKey` field is always in `required` too, so a body that lists the required fields names it among them and never says no other field is required.
- **Seed rows.** A record task writes every row the spec names. Rows the builder makes up stop at 20 per object. More than 200 rows into one object is an `automation` task or an import.
- **Storage fetch.** `storage_by_unifyapps_fetch_records` applies its filter in one shape only (`app-page-build` gives it) and ignores any other with no error. A bind that needs a subset names the rows, and its proof reads back only those rows.
- **Callable binds.** `run_data_source` runs only a source that reads: it refuses a callable (a source that runs an automation) before anything is sent. A bind over a callable is proved by `get_data_sources` (its `inputs.parameters` and `callbacks`) and by the run status the automation's own task reports in `Built so far`, never by `run_data_source`.
- **App visibility.** `set_app_visibility` takes `PUBLIC` (anyone with the link, no sign-in) or `PRIVATE` (sign-in, then permission groups); a code app takes the same two values through `update_code_app_settings`. "Everyone on the tenant" is `PRIVATE`.
- **Test data.** A test makes its own rows with unique values and removes them by the ids it made. It never edits, resets or deletes a row it did not make. Cleaning up rows it did not make is its own task that names them in `deletes`.
- **Page load.** `runBehaviour: "automatic"` runs a source when a block that uses it first shows. At page load it also needs `advancedOptions.timing.runQueryOnPageLoad: true`. A bind for a source that loads with the page names both.
- **Block names.** A block name is an identifier: letters, digits and `_`, unique in the app, camelCase by role (`orderList`). Never a label like "Order list".
- **Block descriptions.** A block stores a name and no description: `create_block` and `rename_blocks` take a name only. A body never asks that every block has a description.
- **Variable, function and data source names.** The tool refuses a name that is not an identifier (a letter first, at least 3 characters, only letters, digits and `_`) or that is a reserved word, and writes nothing; its error names the word. Names a planner reaches for often are reserved, such as `values`, `value`, `item` and `state`, so a spec or body that fixes a name gives it a domain word (`contractValues`, never `values`).
- **Evaluation automations.** `check_evaluation_automations` lists every evaluation automation the tenant lacks, often one no task uses. A dataset, metric or experiment body names the writes it makes and stops only when an automation one of them needs is missing, never on "anything missing".
- **Counts.** Never write a total next to a list. Say "every field the body lists" or "every row listed".
