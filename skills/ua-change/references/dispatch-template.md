# Builder-agent messages

The CLI writes every builder message from this file. `plan ready <planId> --mark` marks each batch running and writes its message to `.sessions/<sessionId>/batches/<agentName>-<k>.md`; the router sends the agent a prompt that says to read that file. Claude Code's auto mode judges a builder's calls by that prompt and never reads the file. So the prompt also names the tenant and the environment it answered, each task's kind and entity, each yes the person gave, and the folder of the UnifyApps Headless CLI the file's commands run (`sendPrompt` in `scripts/lib/dispatch-message.mjs`). The router copies the file's path by hand, so the prompt also says that `<agentName>-<k>.md` is the only file of that name under `.sessions`: `<k>` goes past every earlier message of that agent in any session. The layout of a message is code (`scripts/lib/dispatch-message.mjs`). The words are here: the CLI copies the `## Rules` and `## Report` sections below into every message and fills only `<planId>`, `<sessionId>` (the router's session, which every `ua.mjs` command of the builder names, since a builder's own session id can differ), `<workFolder>` (`.sessions/<sessionId>/work/<agentName>/`, made before the batch is sent), `<deleteTools>` (the delete gate, made from `DELETE_TOOL_NAMES` and `DELETE_OPS` in `scripts/lib/contracts.mjs`), `<reportFile>`, `<reportCommand>` and `<agentName>`. Change the words here, not in code.

Every message is the full message, also when the batch goes back to an agent that already ran: a bind after its layout, or a retry. So a batch whose agent cannot be reached goes to a new agent with the same file. An app-agent batch is one page, the `app` task of one app, or the publish of one app. A code-app-agent batch is the tasks of one code app. A message holds, in order:

1. `Tenant <host> · plan <planId> "<planTitle>" · you are <agentName>.`, then `INTERACTIVE: false`, then the number of tasks and the order rule.
2. One block per task:
   - `Task <id> "<title>" (<kind>) · entity <kind> <name> [id]`, with the page's app when it has one.
   - `Needs:` the tasks of this list it waits on, or `nothing in this list`.
   - `Body, verbatim:` the task body, word for word.
   - `Job:` the page's job line from the spec, on the layout and the review task of a page that has one, then `Design, regions in page order:` and one line per region of the page's design block, `<weight> · <region>: <what it shows and does> · serves <part of the job>`, and `App look:` its app's look line when the plan wrote one, also on an `app` task. `plan create` copies all three, so a builder never works from a line the plan left out.
   - On a `page-review`: `Review round:`, `Shots:` (the files reported by the task it judges, the page's bind or its layout, which `plan create` stored in its `reviewedTaskId`, never the builder's own answers about them) and, from round 2, `Earlier findings` and `Earlier scores` (the last review's score for each quality). On a task a review sent back: `Review found, in your last shots:` and the findings, one per line.
   - `Proof:` the proof, with `[visual: shots at two widths, see Rules]` when the task has a job, else `[visual: take a screenshot]` when the task is visual.
   - `From the spec:` every line of the plan's spec that names the task's entity, from `Current state (READ)`, `Contract`, `Business rules` and `Touches` (an older stored brief gives `Changes` and `Rules` instead), each with its section, except the job, design and look lines the block already shows above; then `Full spec:` and the path of the whole spec.
   - `Built so far, read back:` one line per done task it depends on: entity, ids, read-back lines and its `handover:` notes. For a bind this carries what its layout handed over: page id, block ids by role, form field keys and `var_` ids. A `page-review` gets only its layout's line with its ids, for the page id it reports: the builder's read-back would tell it what to see.
   - `Last attempt:` the task's last error, or `none`.
   - `Answer from the person:` the answer to the task's question, or the person's newest words for its retry; for a deploy, a publish or a delete that may go ahead, also its yes (`yes, deploy <name>. …`, `yes, delete <what>. …`); or `none`.
3. `Memory — corrections: … · decisions: …` from the solution memory. Past 4,000 characters it names the `memory get` command to read it in full instead, with only the most recent few of each kind inlined.
4. `Rules:` and the section below.
5. `Report:` and the section below.

## Rules

- Earlier writes may have landed. Read each entity by name before you create it, and update it if it is already there. On a retry (`Last attempt` is filled), what an earlier try of this same task made is this task's own: a body that says to stop when the entity already exists means one made by someone else.
- Your work folder is `<workFolder>`. Write every file of your own there and nowhere else: a script, an `argsFile`, a `.ts` file for `codeFile`, notes. Other builders run beside you and share Claude's scratchpad and `/tmp`, so a file there can be overwritten under you.
- Plan your reads before your first call: one ToolSearch for every tool these tasks need (the tool table in your agent file), one batch of Read calls for the files they need ("What you can read"), and every knowledge sheet they write in your first knowledge read.
- Read the cache before any read tool. `entity context object|automation|app|page <id> [--app-id <id>] --json --session <sessionId>` (the same `ua.mjs` and the same `--session` as your `plan report` command; add it to every `ua.mjs` command you run: a builder's shell may not carry this session's id, and without it every command answers `NOT_STARTED`; an entity your task creates has no id yet, so name it with `--name "<name>"` instead, and a name the cache does not hold answers `miss`) holds every entity the solution links: an object's schema (fields, types, required, indexes), an automation's nodes, inputs, outputs, version and deploy state, an app's navigation, mode (code or config), access (PUBLIC or PRIVATE) and deployed version, a page's blocks, layout, data sources and events. A `hit` is the state as this folder last saw it: every UnifyApps Headless write here marks the copy stale before it leaves, but a save someone else makes elsewhere does not. For any fact the hit holds, make no tool call; whichever tool would have read it, the answer is already in the hit. Call a read tool only for what the cache never holds — stored rows, connections, runs, knowledge sheets, an automation's source, published version history — or on `miss` or `stale`. The read-back after your write is always live. Every write that changes an existing entity names the version you read it at (`expectedVersion`, `expectedVersions` or `version`, as the tool's input says); the hit's version is fine, and most such writes are refused with `VERSION_REQUIRED` before they are sent. A first save of something that has no version yet leaves it out. When a write answers "Version changed", someone saved after your read: read it live, rebuild the write on the latest state with only this task's changes, and send it once more with the new version. An incompatible change to the same value is a failed task, not permission to overwrite. A code app is never in the cache: its source is the checkout `get_branch_codebase` writes, and `get_code_app` reads its state.
- For one fact, read the cache shaped, not the whole body: a page's body is ~140 KB, these are a few lines. Run them with the same `ua.mjs` and `--session <sessionId>`. A page: `cache blocks <pageId> --app-id <interfaceId> --name <displayName>` (one block; `--field component.appearance` for one key), `cache outline`, `cache events` (`--name <block>` for one block and what it leads to), `cache form`, `cache keys` (`--name <function or variable>` for one, whole, a function's body included), `cache ds`, `cache deps`, each `<pageId> --app-id <interfaceId>`. An app: `cache nav <interfaceId>`, `cache paths <interfaceId>`. An object: `cache obj <objectId>`. An automation: `cache wf <workflowId>`, with `--contract` for its inputs and outputs or `--deps` for what it calls and what calls it. An AI agent: `cache agent <agentId>` (its record — models, instructions preview, default tools on, what is deployed; its attached tools, skills, knowledge, tasks and guardrails are live reads it names). Each answers `miss` or `stale` the same way and names the tool to use instead. NEVER write your own script to search the cache files; if no command answers the question, use `entity context` or the read tool.
- Dry run only where a tool has one that protects something: the object and API Platform deletes that need the count their dry run reports, `delete_env_variables`, and the custom connector deletes. `apply_page_edits` and `compile_and_save_workflow` have no dry run and `apply_object_batch` needs none: each checks everything first and writes nothing when a check fails, so send it once. No tool takes the plan id as a flag, and you never write it: the bridge adds `[ua plan <planId>]` to the end of a deploy's or publish's `deploymentNotes` by itself. `publish_agent` and `deploy_agent` take no `deploymentNotes`, so an AI agent's publish or deploy carries no tag; that is not an unverified line. Re-read what you wrote and quote the lines. Anything a tool did not show is UNVERIFIED, with the one check that would settle it.
- Start every `readBack` line with this task's entity name or one of its ids. `plan report` puts the entity name in front of the lines of an `ok` entry that names neither, but naming it yourself is clearer: write `Dispatch Order 6ab624de…: deploy_workflow returned ok:true, storedVersion 2`, never `deploy_workflow returned ok:true, storedVersion 2`. `plan report` refuses an `ok` entry with no read-back line.
- Read the error, two tries. When a call fails, read the error and say in one line what it means. A clear error: fix exactly what it names and try again. An unclear one (an internal error, a 5xx, a timeout, no hint): one cheap read to see whether the write landed, then the same call once more. Apart from that one retry, never resend an input that already failed. Stop after the 2nd failed try of one step: do it one different way (2 more tries), or report the task failed with the tool, the last input and the last error.
- Tasks that do not need each other may run in parallel tool calls.
- An `object` or `automation` task is built to stay fast, by your speed skill (`object-performance` or `automation-performance`). Its `ok` entry ends with that skill's `speed:` note in `notes`; `plan report` refuses an `ok` entry without one, unless the task deletes its entity. A read that needs an index on an object is an `index needed:` note plus `plan_change: absorbed`: the router adds an object task for it.
- Do only the tasks in this message. Another task on the same page or entity (its bind, a later fix) comes in a message of its own, perhaps to you: never do it early, because `plan report` cannot record it and the work is done twice.
- A fact you found that a later task must follow (an id it needs, a platform behaviour that changes how it builds) goes in the `notes` of the task that found it as one line starting `handover:`. `Built so far` passes those lines to every task that waits on yours; no other note reaches them.
- If a task fails, do not start the tasks of this list that need it. Report them as not_started and carry on with the rest.
- A task with a `Job:` line is built from that job: a `page-layout` builds its regions, and a `page-bind` keeps them while it fills them with data. The task whose Proof says `shots at two widths` (the page's bind, or its layout when the plan does not bind the page) carries a `design` report (see Report) of the page as it stands then; `plan report` refuses an `ok` entry without it. A `page-review` shows the same `Job:` line only to judge the shots by, and takes none of these steps. The steps, in this order:
  1. The regions come from the message's `Design`, in page order, each with its weight and the part of the job it serves. Build those regions, top to bottom in that order; the `lead` region gets the most room and the strongest type. A `later` region is built one click away, where its line says (a drawer, a tab, a detail page), and is not in the shots. A region that serves no part of the job does not go on the page.
  2. Build it. When the message has `App look:`, the colours, font, text sizes and weights, corners, gaps, grouping, depth, icons, bold thing and motion come from it, as `app-craft`'s `references/app-look.md` § Apply it on every page says, never from you.
  3. Open the page's preview URL with `open-page`, run `page-shot 1440` and `page-shot 1366` in the same browser, and Read both files. Look at them the way the person will: for each region of the Design, say what you see of it, and whether it does the job you gave it. Then answer three questions from the shots: `firstSeen`, what the eye lands on first and which part of the job it serves; `signals`, how each value in the job's `signals` shows its state; `dataOrder`, whether the rows and numbers are complete and in the order the page says.
  4. Fix what the shots show is wrong or unfinished, then take both shots again and look again. A problem you cannot fix goes in `unverified` on a line that starts with `design:`, with the reason. "It is only the window size" is not a reason: the person's window is that size too.
  5. Then a second agent, which did not build the page, judges your shots against the job. When your message says `Review found, in your last shots:`, that review sent the page back: fix each finding, or say in `unverified` on a `design:` line why it cannot be fixed, then take both shots again and report as before.
- Never open a browser unless a task says visual. Never dispatch agents. Release finished work only in a deploy or publish task, which waits for the person's yes through `plan confirm` when the plan asks. When its `Answer from the person` says yes, the yes is already given: release it and do not ask again, even if its body says to wait for one. An `automation-shell` deploys its stub with no yes. An AI agent is published only in a `publish` task on it, never inside its `ai-agent` task. Deploy anything else only when the task's own body says to.
- Before a call that deletes — <deleteTools> — you need the person's yes to that delete. A call that sends `dryRun: true` deletes nothing and needs no yes; every other call to these tools does, even one that only deletes rows this same task created (its own test rows). A task that names what it deletes was asked about before it was sent, so its `Answer from the person` carries that yes: make the delete it names and do not ask again. For any other delete, stop and ask the person first as `needs_confirmation`, then call it only once their answer comes back a yes. This holds in every plan, and never depends on the person's yes to the plan — that yes covers only the deploy and publish lines its preview named. The tenant bridge also refuses every delete with a `CONFIRM_REQUIRED (d_…)` line, even one your task's answer already allows. Then stop that step and report needs_confirmation with that line in `error`. When the answer comes back a yes, make the exact same call again. Deleting a block, a page variable, a page function or a folder is routine page editing, not deleting an entity, so those need no confirmation.
- On a 401/403, stop and report every unfinished task as auth_expired. One exception: a code-builder reply whose hint says Code Builder's engine refused the sign-in before doing anything. Signing in again does not change what that engine accepts, so report those tasks failed with its error.
- A call or command refused for the `AGENT_LLM_TOOLS` permission (the line names it) is not a tool error, so the two tries do not apply: the tenant keeps refusing that person until a tenant admin grants it. Do not send it again, do not reach the same result another way, and send no more tool calls. Report every unfinished task needs_confirmation with that line in `error`. If your `plan report` command is refused the same way, do not run it again: end your reply with the report as one fenced json block. When a later message's `Answer from the person` says it is granted, carry on.
- If a task needs an answer only the person can give, report it as needs_confirmation with the question in `error`, and carry on with the tasks that do not need it.
- In your report, quote a yes as `Answer from the person` gives it. A yes that says the accepted spec names the release is the plan's approval: never report it as the person's answer to that call.
- If `Answer from the person` says no to a task, such as a deploy they do not want, do not do it: report it as declined with their words in `error`. It is skipped with every task that waits on it.
- If a task starts a platform run that takes longer than you can wait (a load of an hour, say), do not sleep or poll. Report it as waiting, with `checkAfter` set to the minutes until its result is worth reading (1 to 120), and say in `error` which run to read. The task comes back after that time with your words in `Last attempt`.
- If Claude Code's auto mode refuses a call ("denied by the Claude Code auto mode classifier"), that is the person's own permission check, not a tool error. Never send the call again in this run, and never reach the same result another way. For your `plan report` command, end your reply with the report as one fenced json block, and put the line `Blocked by auto mode: plan report` just before that block. For any other call, report the task needs_confirmation with `error` set to `Blocked by auto mode: <tool> [<reason>] on <entity name>`. Do not copy the call's input into the report. The router asks the person. When a later message's `Answer from the person` says yes to that call, make it once more.
- A task that fixes a behaviour is `ok` only when you saw its cause yourself (in a live read, a run, or a browser step the task allows) and saw it gone after the change. When you cannot see the cause, change nothing and report needs_confirmation naming what you need, such as an open browser tab; never ship a fix for a cause you guessed.
- If a live read changes later work, put it in that task's `notes` as `plan_change: absorbed`, `plan_change: major` or `plan_change: requirement`. Do not grow your own tasks.
- If the router says the plan is closed, or the report command says the plan is not in progress, stop before any new write.
- If an unexpected step fails, diagnose and fix it yourself within the two tries. Also report anything that got in the way, wherever it sits: UnifyApps Headless (its CLI, skills, agent files), an MCP tool or its knowledge sheets, or the platform. Report it even when the task ended well: a tool that answered success and the read-back showed otherwise; a tool that did something it did not say (added a value, dropped a key); an error that did not say what to fix; a step that needed two tries or a workaround; guidance that was wrong, missing or contradictory; a wrong summary or count; plugin-created repo pollution.
- Write each bug directly to `feedbacks/records.md` as a standalone repair handoff for a coding agent without transcript access: `### <date> · <agent> · <resolved|unresolved>`, then, in order, `Bug:`, `Context:` (operation, relevant input/state and likely surface when known), `Where:` (`UnifyApps Headless`, `mcp-tool`, `platform` or `unknown`), `Evidence:` (exact useful error or expected versus actual plus the shortest reproduction), `Cause:` (`Confirmed: ...`, `Suspected: ...`, or `Unknown — next check: ...`; never promote a guess), and `Regression:` (smallest test or observable check that fails before and passes after). Report what happened and how to see it again; a remedy is not yours to propose, and a `Fix:` or `Prevention:` line steers whoever picks this up before they have looked. After the local write succeeds, add the same block to that task's `notes` as one string shaped `feedback:\nBug: <bug>\nContext: <context>\nWhere: <where>\nEvidence: <evidence>\nCause: <cause confidence and cause or next check>\nRegression: <test>`; JSON-escaped newlines become readable Markdown in saved remarks.
- Separately, when actual work needs a capability that UnifyApps Headless, its tools or the platform do not offer, a step you did by hand because no tool does it, or a tool change that would have made the task much faster (many calls where one list call would do, a read repeated because a tool answered too little), append `### <date> · <agent> · feature`, then `Feature:`, `Evidence:`, `Benefit:`, `Scope:` (affected plugin surface and non-goal), and `Acceptance:` (one observable completion check). Add one task note shaped `feature:\nFeature: <capability>\nEvidence: <observed need>\nBenefit: <reusable value>\nScope: <surface and non-goal>\nAcceptance: <check>`. A feature request applies only when current promised behavior is correct; anything inaccurate, misleading, broken, blocked, or requiring a workaround stays bug feedback even when its remedy adds a capability.
- Use one or two concrete sentences per field, preserve existing entries, and include no secrets or long logs. Do not brainstorm feature ideas; ignore speculative, cosmetic, one-off, or tenant-specific wishes. Do not delegate the recovery or write, and never block, delay, add retries, or broaden the task solely to report either type. Routine tenant-specific dry-run findings caught as designed, confirmation pauses, authentication prompts, and user-declined optional actions remain unreported unless the plugin guidance or error is itself misleading. These records and `feedback:` or `feature:` notes are internal bookkeeping: do not add any prose announcing that you recorded them. If the local write fails, mention it once in `notes` and do not loop on it.

## Report

- You record your own report. When every task in this message is settled, write the report as JSON to `<reportFile>`, one entry per task in this message:
  `{"tasks":[{"id":"<id>","status":"ok|failed|not_started|auth_expired|needs_confirmation|declined|waiting","change":"created|updated|deleted","ids":{},"readBack":[],"unverified":[],"notes":[],"error":""}]}`
- The task whose Proof says `shots at two widths` adds `"design"` to its `ok` entry: `{"regions":[{"region":"","seen":""}],"shots":[{"width":1440,"file":""},{"width":1366,"file":""}],"firstSeen":"","signals":"","dataOrder":""}`, from your last shots, with one region entry for each region of the Design, named as the Design names it. `plan report` refuses the entry when a region of the Design has no entry, when a region lacks `seen`, when a shot file is not a PNG of its width in your work folder (where page-shot writes it), when the shots are not at two of the preview's sizes (1366, 1440, 1680, 1920, 2560), or when an answer is empty.
- A `page-review` task adds `"review"` to its `ok` entry: `{"verdict":"pass|fix","qualities":{"hierarchy":"pass|fix","grouping":"…","alignment":"…","contrast":"…","readability":"…","consistency":"…","states":"…"},"findings":[{"where":"","what":"","job":"","severity":"blocks|polish","quality":""}]}`. `plan report` refuses a verdict other than pass or fix, a quality left unscored, a quality scored `fix` with no finding that names it in `quality`, a finding without where, what, job or severity, a `fix` with no finding that blocks, and a `pass` beside one that does. One review runs per page: a `fix` sends the blocking findings back once, and the review closes when that fix is done.
- A task whose Body is to fix, debug or explain a bug adds `"fix"` to its `ok` entry: `{"rootCause":"","evidence":"","changes":[{"entity":"","before":"","after":""}],"proof":""}`, from the cause you saw yourself (§ Rules, "A task that fixes a behaviour"): `rootCause` and `evidence` name what was wrong and the run id, failing step or config line that showed it; `changes` carries one entry per entity you changed; `proof` is the re-run or read-back that showed the cause gone, quoted as the tool answered, or `"not verified: <why>"` when none was possible. The router copies this into the person's Fix report; an empty field there is an empty line on the ticket.
- Then run this command once, exactly as written:
  `<reportCommand>`
- If it prints an error, read it, fix the file, and run the command once more. A report it refuses (a missing task, an `ok` entry with no read-back line, a wrong `ids.entity`, a page with a job and no `design`) records nothing and spends no attempt: your tasks stay yours until the fixed report goes in. If it says there is no running batch for <agentName>, the report is already recorded.
- Your last reply is only the line the command printed (it starts with `Recorded`), plus every `plan_change:` and `Key file:` note word for word. Do not repeat the report.
- If the command fails twice, end your reply with the report as one fenced json block instead, so the router can record it.
- Run no other plan command.

## Report fields

`ids.entity` holds one id: `plan report` refuses an `ok` entry that joins several there, and a task that built several entities puts the other ids under their own keys in `ids`. Page tasks put the page id in `ids.entity` and the containing interface id in `ids.app`, so the solution link targets the app. Two tasks that name the same entity, such as an agent built and then evaluated, report the same id. `ids.entity` is the id of the task's own entity, never a block, data source or row it made. When the message names the entity's id, or a done task already reported it, `plan report` refuses any other id there and names the one to use. A layout and its bind build one page, so they report the same page id. A record task's entity is its object: `ids.entity` is the object id, and the ids of the rows it wrote go in `ids.records`. `change` is `created` when the task made the entity, `updated` when it already existed, and `deleted` when the task deleted the entity itself (not rows, fields or blocks inside it), so the entity table shows it as deleted with no link. Each `readBack` line must name its entity or quote one of its ids; `plan report` puts the entity name in front of the lines of an `ok` entry that names neither, and refuses an `ok` entry with no read-back line. The Rules say so up front. No task may claim success from the write response alone.
